# 財務モデルの土台を作り直す（2026-09-04・発注者指示）

発注者の問い:「財務計画をHTMLでやっているのが非効率な気がする。エクセルのほうが早い？」

結論: **エクセルには戻さない。ただし「非効率」の感覚は正しい。**
遅いのはHTMLではなく、その下の4つの欠落。ここに挙げるのは発注者が採択した5項目。

- ① シナリオを一級のデータにする
- ③ 財務モデルの計算を1本にまとめる
- ④ 比較ビュー（現状 vs 案）を共通部品にする
- ⑤ 人物マスタを作り、名前をID参照にする
- ⑥ 変更履歴のサブコレクション
- ⑦ 未登録項目（pending）を機械が読める配列に
- ⑧ 金額の意味（当初元本 / 残高 / 申告額）を1列に固定し、画面で明示
- ⑨ 用語マスタ（terms）— **2026-09-04 に着手済み。残りは共有部スレッドへ**

（②「シナリオを画面で編集するUI」は今回見送り。①ができれば後から載る）

## なぜエクセルに戻さないか

エクセルが速く感じるのは**打ち替えて即結果が見える**という一点だけ。それ以外は確実に遅く、危険。

2026-09-04 の実例: ウィズダム有限会社の残高が ¥29,591,920 と出ていて
「30,000,000のはずだが、いつ変わったのか」という疑問が出た。答えは
**台帳は変わっておらず、返済が2026-05に始まっているので残高を引き直した値**だった
（同条件の真佐子・晴信は開始が2027-02なので30,000,000のまま）。
返済表から毎回引き直す作りだから即答できた。エクセルの手打ちなら
「どっちの数字が正しいのか」で止まり、どちらかを消して終わっていた。

## ① シナリオを一級のデータにする（最優先）

### いまの問題

整理案は `assumptions/family-fund` の中の `postPlan` という**隠し部屋**に1本だけ置かれている。

- **1本しか持てない。** 「4%案」と「3%案」、「付け替えあり/なし」を並べられない
- **上書きすると前の案が消える。** 2026-09-04、整理後の金額は
  2,000万 → 5,000万 → 1,000万 と4回書き換えられた。**前の値はもう復元できない**
- **どのカードから参照するのかがURLに出ない。** BSカードは `?sub=norel`、
  家族ファンドカードは `?sub=plan`——同じ「整理後」を別のキーで呼んでいる

### あるべき形

    scenarios/{id}
      label:     "家族ファンド 4%・付け替えあり"
      status:    draft | proposed | approved | rejected | superseded
      base:      "actual"              // 何からの差分か（実績 or 別シナリオ）
      overrides: { … }                 // 前提の【差分だけ】を持つ
      note, source, updatedAt, updatedBy

`overrides` に入るのは、いま postPlan / assumptions に散っているもの:

| 差分の種類 | 例 |
|---|---|
| 借入の置き換え | `finance/loan-kazuyoshi-officer` を3本に付け替える |
| 利率の変更 | 家族ファンド全体を年4%・利息のみに |
| 切替時期 | `switchMonth: "2026-10"` |

### 効くこと

- 複数の案を**並べて比較できる**（これがエクセルに勝てなかった最後の点）
- どのカードからも同じ `?scenario={id}` で参照する。URLキーが1つに揃う
- 承認・却下が `status` として残る。いまは note の日本語文にしか無い
- 既存の `assumptions/family-fund.postPlan` は移行して**廃止**する

## ③ 財務モデルの計算を1本にまとめる

### いまの問題

**元利均等の計算が3箇所にある。**

| 場所 | 何をしているか |
|---|---|
| `functions/src/agency/finance.ts` の `loanState` | 返済表を引いて、ある時点の残高を出す |
| `functions/src/agency/bs.ts` の `liabilityAmount` | 条件未登録なら申告額、登録済みなら導出残高 |
| `yah-os/familyfund.html` の `famYear` | 返済表を頭から引き直して、その年の支払と利息を出す |

3つ目が特に悪い。**カードのHTMLの中に財務モデルが入っている**ので、
- 型検査には載るが、サーバのテスト（`money.test.ts`）には載らない
- 別のカードが同じ計算を要ると、4箇所目が生まれる
- サーバ側でモデルを直しても、カードの中の計算は古いまま残る

### あるべき形

`functions/src/agency/model.ts`（既存）に**返済モデルを集約**し、カードは呼ぶだけにする。

    ・loanSchedule(loan)            … 返済表（1本ぶん・月次）
    ・loanState(loan, asOf)         … ある時点の残高（既存）
    ・loanYear(loan, year)          … その年の支払・うち利息
    ・portfolio(loans, year, scenario) … 上を束ねて、シナリオの差分を当てた結果

`famYear` はこれを呼ぶだけの薄い関数になる。**テストは money.test.ts に集約**する。

移行は1本ずつ。まず `famYear` をサーバへ移し、結果が今と一致することを確認してから次へ。

## ④ 比較ビュー（現状 vs 案）を共通部品にする

### いまの問題

2026-09-04 の1日で、**ほぼ同じ切替を2枚のカードに別々に実装した**。

| カード | 実装 | URLキー |
|---|---|---|
| BS | 「現状【家族ファンド整理前】/ 家族ファンド整理後」ピル。整理後は琥珀の枠 | `sub=norel` |
| 家族ファンド | 同じ文言のピル。KPI3表に効く | `sub=plan` |

3枚目のカードで同じものをまた書くことになる。文言も色もURLキーもズレていく。

### あるべき形

`os-core.js`（または新しい共有ファイル）に部品を置く。

    scenarioSwitch({ onChange })   … ピルを描き、URL（?scenario=）と同期する
    ・文言・色・無効化の作法（効かないビューでは灰色）を1箇所で決める
    ・カードは「いま何を見ているか」を受け取って描くだけ

**注意**: `os.css` はデザインスレッド管轄。見た目の正本は
`design_guideline_yah_os_20260831.md` に先に書いてから検査へ足す（CLAUDE.md ③）。

## ⑤ 人物マスタを作り、名前をID参照にする

### いまの問題（実データで確認・2026-09-04）

`finance` ほかの台帳を横断して数えた結果:

| 表記 | 件数 |
|---|---|
| 山田 一慶 | 14 |
| 山田 晴信 | 4 |
| 山田 眞佐子 | 1 |
| 山田 真佐子 | 1 |

**「眞佐子」と「真佐子」が別ドキュメントに分かれている。** 同一人物。
文字列で名寄せしているので、集計すると2人に見える。BSの家族ファンドの行にも
両方の表記がそのまま並んで出ている。

### あるべき形

    people/{id}
      displayName: "山田 眞佐子"
      aka:         ["山田 真佐子"]      // 過去の表記。移行と検索のため
      kind:        person | company
      note, updatedAt, updatedBy

台帳側は `lender: "山田 眞佐子"` → `lenderId: "yamada-masako"` に変える。
画面は `people` から表示名を引く。**表示名を直せば全カードが一斉に直る。**

会社（ウィズダム有限会社）も同じマスタに入れる——
`BANK_LENDER` の正規表現（`銀行|公庫|信用金庫|…`）で銀行かどうかを判定しているのも、
本来は `people.kind` で持つべき情報（[bs.ts:20](../functions/src/agency/bs.ts:20)）。

### 移行の順序（本番データを触るので慎重に）

1. `people` を作る（既存の表記を `aka` に全部入れる）
2. 台帳に `lenderId` を**足す**（`lender` は消さない）
3. サーバは `lenderId` があればそれを、無ければ `lender` を使う
4. 全ドキュメントに `lenderId` が入ったことを `?action=health` で確認
5. そのあとで `lender` を消す

**4より前に3の後方互換を外さない。** 途中で止まっても画面が壊れないようにする。

## ⑥ 変更履歴のサブコレクション

### いまの問題

`updatedAt` / `updatedBy` はあるが、**前の値は消える**。

2026-09-04 の実例: `assumptions/family-fund.postPlan` の金額を、AIが1日で4回上書きした
（2,000万 → 5,000万 → 1,000万 ほか）。誰がいつ何から何に変えたのかは、もう残っていない。
**金額を扱う台帳としては、これは欠陥。**

### あるべき形

    {collection}/{id}/history/{timestamp}
      at, by, action: set|update|delete
      before: { 変わったフィールドの旧値だけ }
      after:  { 新値 }
      note:   "発注者指示（2026-09-04）"

- 書くのは**サーバの1箇所**（`engine.ts` に write ラッパーを置き、全ての書き込みを通す）。
  各 route が個別に履歴を書く形にしない——書き忘れが必ず出る
- 差分だけを持つ（ドキュメント全体をコピーしない）
- 対象は**金額・係数・人の判断を持つコレクション**（`finance` / `assumptions` /
  `scenarios` / `bsAdjustments` / `items` / `equipment`）。ログ類は対象外
- 画面には出さなくてよい。まず**残すこと**が目的

## ⑦ 未登録項目を機械が読める形にする

### いまの問題（実データ・2026-09-04）

`pending` に**日本語の文章**が入っている。台帳全体で6件、`conditionsUnknown: true` が5件。

| ドキュメント | pending の中身 |
|---|---|
| `finance/loan-harunobu-corp-3m` | ①いつ借りたか ②返済の予定を定めるか ③年4%を付けるか |
| `finance/loan-kazuyoshi-officer` | ①当初の内訳（いつ・いくら入れたか）②2026年以降の増減 ③返済の予定を定めるか ④年4%を付けるか |
| `assumptions/family-fund` | ①個人間の貸付80,000,000を法人へ付け替えるか ②役員借入金93,031,628と晴信3,000,000がfinance未登録 ③実行時期 |
| `assumptions/personal-income` | 分配金の普通／特別の内訳（運用報告書） |
| `assumptions/succession-readiness` | 団体信用生命保険・経営者保険の加入状況が未登録 |
| `assumptions/target-model` | ①地場工務店1社への総額見積 ②複数の収益仲介へのcap確認 ③土地の仕入れルート |

**人間は読めるが、機械は何ひとつ拾えない。** 結果:

- `?action=health`（数字の信頼度）に**この6件が1つも出てこない**。
  「何が未確定なのか」を機械が集計できないので、健全性の判定に入らない
- 画面には `conditionsUnknown: true` から「条件一部未登録（申告額）」という
  **一律の文言**しか出せない。何が未登録なのかは出せない
  （BSカードの家族ファンドの行がまさにこれ）
- 解消したときに、文章のどの丸数字を消すのかが人の判断になる。消し忘れが残る

### あるべき形

    pending: [
      { id: "start-month", label: "いつ借りたか", field: "startMonth",
        blocks: "balance", status: "open", since: "2026-08-31" },
      { id: "rate",        label: "年4%を付けるか", field: "rate",
        blocks: "interest", status: "open", ref: "assumptions/family-fund" },
    ]

| キー | 意味 |
|---|---|
| `field` | どのフィールドが埋まれば解消するか。**埋まったら自動で閉じられる** |
| `blocks` | 何が導出できないか（`balance` / `interest` / `schedule`）。健全性の判定に直結 |
| `status` | `open` / `resolved`。解消の記録が残る |
| `ref` | 判断の待ち先（別ドキュメント） |

`conditionsUnknown: true` は**廃止**する。`pending` に `blocks: "balance"` が
1件でもあれば「条件未登録」だと機械が導ける——真偽値を別に持つ必要がない
（いまは両方あって、片方だけ直すとズレる）。

### 効くこと

- `?action=health` が**未確定を自動で集計**する。カードの状態ドットに反映される
- 画面に「何が未登録か」を出せる。「条件一部未登録（申告額）」という一律の文言が
  「返済開始月と利率が未登録」になる
- `field` が埋まった時点で自動的に閉じるので、消し忘れが構造的に起きない

## ⑧ 金額の意味を1列に固定する

### いまの問題

**「当初元本」「現時点の残高」「申告額」が、画面上の1つの列に混ざって落ちてくる。**

`liabilityAmount`（[bs.ts:40](../functions/src/agency/bs.ts:40)）はこう分岐している:

    条件が未登録 → amountReported（申告額）、無ければ principal（当初元本）
    条件が登録済 → 返済表から導いた残高、導けなければ principal

つまり同じ列に3種類の意味の数字が並ぶ。実際に混乱が起きた例（2026-09-04）:

| 行 | 出ている額 | その正体 |
|---|---:|---|
| ウィズダム有限会社 | ¥29,591,920 | **導出残高**（2026-05から4回返済済み） |
| 山田 真佐子 | ¥30,000,000 | **当初元本**（返済開始が2027-02なのでまだ減っていない） |
| 山田 一慶 | ¥93,031,628 | **申告額**（条件未登録） |

同条件の3本が並んでいるのに1本だけ額が違う。発注者から
「これは30,000,000円だけど！？いつ変わったの？」という疑問が出た。
**台帳は正しく、画面が意味を伝えていなかった。**

さらに `loan-kazuyoshi-harunobu-a` の note には、本人がこう書いている——
**「当初借入額か現在残高かは未確認」**。台帳の中にすら意味が確定していない金額がある。

### あるべき形

サーバは**額と一緒に、その額が何なのかを返す**。

    { amount: 29591920,
      basis: "derived",              // derived | reported | principal
      asOf:  "2026-09-04",
      principal: 30000000,           // 当初元本は常に併記
      note: "2026-05開始・4回返済済み" }

`basis` はすでにコードの中の分岐として存在している。**返していないだけ**なので、
サーバ側の変更は小さい。

画面は `basis` を見て添える:

    山田 真佐子          ¥30,000,000   当初元本（返済は2027-02から）
    ウィズダム有限会社    ¥29,591,920   残高（2026-09-04時点・当初 ¥30,000,000）
    山田 一慶            ¥93,031,628   申告額（条件未登録）

台帳側では、`principal` は**常に当初元本**という意味に固定する
（`amountReported` に当初額を入れてよいのは、当初額しか分かっていないときだけ）。
意味が未確定のものは ⑦ の `pending` に `{ id: "amount-basis", blocks: "balance" }` を立てる。

### 効くこと

- 「なぜこの1本だけ額が違うのか」が画面で完結する。台帳を掘りに行かなくてよい
- 当初元本と残高を**並べて**見せられる。BSは残高、融資カードは両方、という出し分けが可能
- 意味の未確定が `pending` に載るので、⑦ の健全性チェックに自動で乗る

## ⑨ 用語マスタ（terms）— 2026-09-04 に着手済み

### やったこと

全カードの `<th>` を機械的に洗い出したところ、同じものが違う語で出ていた。

| 正式名 | 画面に出ていた表記 |
|---|---|
| 残高 | 残債／借入残高／期末残高／年初残高／年末残高／月初残高／月末残高／残高の合計 |
| 当初元本 | 元本／当初借入額／借入額 |
| 支払利息 | 年の利息／うち利息／利息 |
| 元利返済 | 返済(元利)／年間の返済／返済 |
| 経常利益 | 利息を引く前／利息前収益 |
| 返済原資 | 利息前収益＋償却 |

    terms/{id}
      group:   借入 | 損益 | 指標 | 資産
      label:   正式名          ← これが正
      aka:     [ いま画面に出ている表記 ]   ← 移行のとき何を置き換えるかの一覧
      def, formula, unit, field

22件を登録済み。`?action=terms` で返る（finance.route.ts）。

### 画面への効かせ方（発注者の判断・2026-09-04）

**独立カードは作らない。** 財務カテゴリーは「数字を見に行く場所」で、
数字を持たない用語カードを混ぜると一覧の意味が薄まる。用語はメタ情報なので
`ssot.html`（メタのカード）に置いた。

**本命はツールチップ。** 用語集は単体では読まれない。今日の混乱
（ウィズダムの額が当初元本か残高か）は、一覧を見なかったからではなく
**その場で意味が分からなかった**から起きた。だから語が出ている見出しに定義を出す。

| | 状態 |
|---|---|
| `terms` の登録（22件） | 完了 |
| `?action=terms` | 完了 |
| `ssot.html` の「4. 用語」 | 完了（台帳から引いて出す。焼き込みなし） |
| 家族ファンドのKPI3表のツールチップ | 完了（`th()` ヘルパー） |
| **他の全カードのツールチップ** | **未。共有部スレッドへ** |
| **見出しを正式名に寄せる（aka → label）** | **未。共有部スレッドへ** |

### 共有部スレッドへの申し送り

- `th()` 相当のヘルパーは、いま `familyfund.html` の中にある。**共通化して `os-core.js` へ**。
  カードごとに書き写すと、③ の「計算が3箇所」と同じことが見出しでも起きる
- 見出しを正式名へ寄せるのは**一斉書き換え**になる。カードスレッドが止まっている時間に、
  即 commit → push（CLAUDE.md ②の作法）
- 点線の下線（`th.has-term`）の見た目は**デザインスレッド管轄**。
  正本のガイドラインに書いてから検査へ足すこと

## 進め方

| 順 | 項目 | 理由 |
|---|---|---|
| 1 | ⑥ 変更履歴 | 先に入れないと、以降の移行作業そのものが記録されない |
| 2 | ① シナリオ | ③④が参照する土台 |
| 3 | ⑤ 人物マスタ | 独立して進められる。①と並行可 |
| 4 | ③ 計算の集約 | 1本ずつ移す。移すたびに数字の一致を確認 |
| 5 | ⑧ 金額の意味を返す | サーバの変更は小さい。混乱が実際に起きている箇所 |
| 6 | ⑦ pending の構造化 | ⑧と同時に入れると、health への反映が一度で済む |
| 7 | ④ 比較ビューの共通部品 | ①ができてから |
| 8 | ⑨ 用語の一斉書き換え | ツールチップの共通化を先に。全カード横断なので最後 |
