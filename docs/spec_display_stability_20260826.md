## 1. 症状の分解と原因判定（確定）

動画に写っていた「揺れ」は1つのバグではなく、**独立した4つの機構**が重なったもの。

### 症状A: カードを開いた直後、表が丸ごと消えて素のタブバーが露出し、再描画される（動画2本目の最後・最重要）

- フレーム解析: 融資の返済カードで 29.6s に表が描画 → 30.1s に全消滅＋埋め込み前の縦タブバー（融資表/正本）が露出 → 30.6s に再描画。
- **原因（確定）: index.html L515-521 の認証リスナー内 `if (!first && f && f.src) f.contentWindow.location.reload();`**
  - 「素のタブバーの露出」はドキュメントの**再パース時にしか起きない**ことをコード全数検査で確認（os-embed.js のサブナビ移設は DOMContentLoaded 内で一度きり・side を再生成するコードは存在しない）。
  - マスク（読み込み中表示）なしで再パースを起こせる経路は、コード全体でこの1行だけ。
  - 引き金: このガードは引数 `u` を一切見ておらず、**2回目以降の onAuthStateChanged 発火を全て「ログインし直し」とみなす**。Firebase v10 の onAuthStateChanged は uid 不変なら再発火しない（SDK 内部に lastNotifiedUid ガードがある——当初の「同一ユーザーのまま再発火する」仮説は敵対検証で反証された）が、**uid が実際に変わるイベントは全てここを通る**: 別タブでのログイン/ログアウト、トークン失効による強制サインアウト→復帰、そして親子フレーム（index と iframe 内カード）が各自 Firebase を初期化し `setPersistence(browserLocalPersistence)` でストレージ層を移送し合う際の同期（user→null→user と uid が往復する）。発注者のブラウザは yah 系タブを常時多数開いており、条件が揃う。
  - さらにこのリロードは openKey() の読み込み中マスクを**通らない**ため、ユーザーには「表が消える→素のタブバー→モック→キャッシュ→本データ」が生で見える。

### 症状B: 「読み込み中…」が長すぎる（数秒の空白）

- **原因（確定）: 2026-08-26 の応急修正（コミット e55f34b）自身の副作用。** iframe の可視化を `load` イベントに紐づけたが、`load` は全サブリソース——**gstatic の Firebase SDK を含む**——の取得完了まで発火しない。カードは本来「静的モックが即ペイント」される設計なのに、それを自分で隠している。高速回線でも実測 約0.6秒、低速回線では数秒。ネットワーク断では永久に「読み込み中」のまま（タイムアウトなし）。

### 症状C: 左メニューが一瞬空になり、数秒後に項目が一斉にポップインする

- **原因（確定）: 既定フィルタ「稼働中」×ドット初期値の設計衝突。** 全ドットは JS 起動時に灰色（d-na）へ初期化され、applyFilter() は「d-ok でない項目を隠す」ため、**health 応答（Firebase SDK 取得＋auth 復元＋fetch で数秒）が届くまでメニューがほぼ空**になる。さらに HTML 側はドットを d-warn（赤）でハードコードしているため、遅い端末では「赤ドット付き全リスト→空→青のみ出現」と三段に揺れる。health 取得失敗時はメニューが空のまま。

## 2. 恒久対策の設計

### P0 — 症状を直接消す（index.html＋os-embed.js・共有部のみ・計1人日）

1. **自発リロードの全廃（症状A）**: L520 の `contentWindow.location.reload()` を **postMessage("auth-changed") に置き換える**。カード側は os-core.js が受けてデータ再フェッチのみ行う（画面は消えない）。ログアウト（uid→null）の時だけは従来どおりリロードでモックに戻す。uid は `u?.uid ?? null` に正規化し、初回発火で lastUid を種蒔きしてから比較する（単純な `uid !== lastUid` 一行置換は、永続ログイン時の初回発火を「変化」と誤判定して無駄リロードを生むため不可——敵対検証で確認済み）。
2. **可視化トリガの是正（症状B）**: 「load イベント待ち」をやめ、**os-embed.js がサブナビ移設完了直後に親へ postMessage（例: os-embed-ready）を送り、親はそれを受けて表示**する。安全網として (a) frame.onload でも表示（os-embed を読まないページ・エラーページを回収）、(b) 2秒のタイムアウトで強制表示。readyState ポーリング案は「interactive 時点ではサブナビ未移設」（DOMContentLoaded は module script 取得完了まで遅延する）ため不採用——低速回線でこそ壊れることを敵対検証で確認済み。
3. **メニューの遅延ポップイン解消（症状C）**: health 未取得の間は「稼働中」フィルタでも d-na（灰）を隠さない（＝初回は全件表示し、health 到着後に絞る）。HTML ハードコードの d-warn は d-na に統一。前回の health 結果を cachePaint（localStorage）して即座に前回の見え方を復元する。
4. **D-1〜D-4 の同時修正**: `frame.src="about:blank"` 化（replaceState を先に）／自動 showHome() は「初回ロードかつ未操作」の場合に限定／URL無し分岐で frame.onload=null＋進行中ロード打ち切り／同一カード再クリックは no-op。

### P1 — 構造で塞ぐ（共有部・計2〜3人日・P0の翌スプリント）

5. **iframe キープアライブ**: 単一 iframe の src 差し替えをやめ、**カードごとに iframe を生成して非表示保持・再表示**（LRU 上限5枚）。訪問済みカードへの切替は display 切替のみ＝空白ゼロ。ログイン後の idle 時間に主要カードを先読み。
6. **認証の親フレーム一元化**: embed 時は子ページの Firebase 初期化をスキップし、**親の auth / getIdToken を window.parent 経由で再利用**（同一オリジン）。子の SDK ロード待ち（空白の主因）と、親子の setPersistence 相互作用（症状Aの引き金）が両方消える。index.html に重複している Firebase init も os-core import に統一。
7. **描画パイプラインの共通化**: os-core.js に `boot({cacheKey, fetch, render})` ヘルパー（30行程度）を追加——「キャッシュがあれば即描画→本フェッチ→**内容が変わった時だけ再描画**」を正本化。maintenance の焼き込みモックは未ログイン時のみに限定。各カードの置き換えは各カードスレッドが自分の番で30分ずつ（一斉書き換え不要）。
8. **embed クラスの同期付与**: 各カード head 先頭の1行インラインスクリプトで `?embed=1` 判定→ documentElement にクラス付与（D-6）。os-embed の s= 復元は `<a href>` を除外（D-7）。トップバー高さは CSS 変数 --topbar-h に一本化（D-5）。

### P2 — 再発を防ぐ足場（later・四半期判断）

- 共通クロームの Custom Element 化（`<os-topbar>`）＋新カード用 _template.html。topbar コピペの微差分ドリフト（finance の旧ドット等）を根絶。
- 左ナビ/LINKS のデータ化（CARDS 配列1つに統合。1行数千文字の diff 不能 HTML を解消）。
- os-embed の DOM 移植を宣言的タブ（data 属性＋CSS grid-area）に置換。
- finance.html の KPI ドット localStorage 保存は SSoT 違反として撤去（融資カードスレッドへ申し送り）。

## 3. フレームワーク導入の評価（Astro 等）

**結論: 見送り。** 理由:

1. 今回の症状は**全てランタイム問題**（iframe 切替・auth 二重初期化・三段描画）。ページは既に静的で、ビルド時テンプレート化では1つも解消しない。
2. ビルド工程は「複数 Claude スレッドが 1カード=1HTML を直接編集 → --preview で即確認」という並行運用の根幹を壊す。共有コンポーネントはカード間にコンパイル時依存を作り、共有部1本スレッド体制の分離が形骸化する。
3. SSG の主目的（マークアップ重複排除）は P2 の Custom Element＋雛形でビルド無しに達成できる。

同様に **軽量SPA化（iframe廃止）も見送り**——iframe が無料で提供している障害隔離（1カードのバグが他カードを壊さない＝並行スレッド運用の安全装置）と名前空間分離を失い、全カード書き直し10人日超に見合う残存問題が P0/P1 後には無い。**htmx による断片差し込みも同じ理由で見送り**（script 実行とスタイル隔離を自前で再実装することになる）。iframe 構造は維持し、P1 の「キープアライブ＋親 auth 引き継ぎ＋パイプライン統一」で症状を構造的に消すのが、移行工数最小かつ運用制約を壊さない解。
