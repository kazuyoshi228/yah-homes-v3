# 直接予約基盤 P1 — 深層リスク追補レビュー

**前提:** 前回レビューのP0/P1/P2、状態機械、Saga、Webhook冪等化、規約・名簿・権限・運用Runbook・限定本番がすべて実装済みであること。  
**結論:** **なお穴はあります。** しかも多くは「機能が動くか」ではなく、**正しい処理を繰り返しても事故になる境界**、**外部システムと人の変更**、**復旧・会計・物理運用**にあります。

> この段階での最大リスクは、APIの失敗ではありません。**“再試行可能な設計”を過信すること、基幹外で発生する変更を検知しないこと、そして障害後に何を正とするかを決めていないこと**です。

法令・個人情報に触れる部分は設計上の論点であり、正式な法的助言ではありません。ローンチ前に専門家の確認を前提としてください。

## エグゼクティブ判定

前回の改善が完了していれば、通常の予約作成・決済・取消の失敗モードには相応に強くなります。しかし、本番の重大事故は次の4つの場面で起きます。

| 失敗の場面 | なぜ残るか | 典型的な結果 |
|---|---|---|
| **再実行と古い処理** | キューもDBトランザクションも「一度だけ」を保証しない | 取消済み予約が古い作成タスクで復活、二重メール、二重外部操作 |
| **基幹外の手作業変更** | Beds24管理画面、Stripe Dashboard、メール設定、規約・料金ルールはコード外でも変わる | 自社画面の価格・取消期限と基幹実態が乖離 |
| **障害からの復旧** | Firestoreの復元は単に本番を巻き戻す機能ではない | 既に外部で確定した決済・予約を再実行または消失扱いにする |
| **責任の境界** | 会計、個人情報、物理的な宿泊提供、緊急時対応はアプリの成功では完結しない | 売上が帳簿と合わない、名簿未回収、現場で宿泊者対応が止まる |

## 1. 最も深い技術的な穴 — 「冪等」の実装契約

### 1.1 Sagaを作っても、古いタスクが最新状態を壊し得る

状態機械と冪等キーを入れても十分ではありません。たとえば、予約作成タスク `A` が遅延している間に、顧客取消タスク `B` が完了したとします。その後に `A` が再配信され、単純に「まだBeds24 IDがないから作る」と実行すれば、**取消済みの予約を再作成する**ことが起こります。

Cloud Tasksは少なくとも一回の配信を保証する設計であり、まれに複数回実行され得るため、ハンドラ自体の冪等性が必要です。[1] また、Firestoreトランザクションも競合時に関数を複数回実行し得るため、トランザクション内部にBeds24呼出、Stripe操作、メール送信を置くのは禁物です。[2]

| 必須制御 | 実装要件 |
|---|---|
| **状態遷移のCAS** | 各ジョブは `expectedStatus` と `stateVersion` を持ち、Firestoreのcompare-and-setで「想定した版のときだけ」実行権を得る。 |
| **fencing token** | 外部操作前に単調増加するoperation versionを確保し、古いワーカーが新しい状態を更新できないようにする。 |
| **外部操作台帳** | `operationId / provider / action / providerId / requestHash / requestedAt / response / finality` をappend-onlyで保存する。予約本体のstatusだけを証跡にしてはならない。 |
| **永続的な冪等判定** | キューのタスク名重複排除は削除後最大24時間のため、会計・予約操作の冪等性をこれに依存しない。[1] 少なくとも法定・会計・紛争対応期間に見合う操作台帳を保持する。 |
| **外部結果の照会優先** | timeout時は「失敗」と仮定して再送しない。まずStripe/Beds24の外部参照値で、実行済みかを照会する。 |

**追加受入試験:** 作成・capture・取消・返金の各タスクを、意図的に24時間超遅延、重複、順不同、途中で手動キャンセルした状態で再投入し、現在の状態を破壊しないことを証明してください。

### 1.2 「どちらが正か」を属性単位で決めないと、日次突合が破綻する

Beds24を在庫・料金のSSOTと決めても、すべての項目の正がBeds24とは限りません。決済の最終状態はStripe、同意証跡は自社、集客帰属は計測基盤、名簿は法定保管領域、予約表示はミラーです。ここを予約単位で曖昧にすると、「差異が出た」後に誰も直せません。

| 属性群 | 正とするシステム | 片方向の同期 | 差異時の原則 |
|---|---|---|---|
| 在庫・客室・料金・予約日程 | Beds24 | Beds24 → 自社ミラー | 自社は上書きしない。必要ならBeds24へ人が補正。 |
| 支払・返金・紛争・入金 | Stripe | Stripe → 自社会計台帳／表示 | Stripeイベントと管理画面照会で確定。Beds24請求書とは別途照合。 |
| 購入意図・同意・内部操作履歴 | 自社のappend-only台帳 | 自社 → 必要最小限をBeds24 | 誤更新は訂正イベントで残し、履歴を書換えない。 |
| 宿泊者名簿・旅券写し | 分離した法定名簿保管領域 | 必要範囲のみ運営へ | 予約DB／分析DBへ複製しない。 |

この**属性別SSOT表、更新権限表、同期方向表**は設計書に必要です。特に「Beds24の予約を運営が直接変更したとき、自社がStripeを自動返金するか」は、絶対に暗黙にしてはなりません。原則は、**外部手作業変更を検出して `MANUAL_REVIEW` に止める**ことであり、自動追随ではありません。

## 2. 復旧設計の穴 — バックアップは予約整合性を戻さない

### 2.1 Firestore復旧後にジョブをそのまま再開してはいけない

Firestoreの定期バックアップは新しいデータベースに復元され、TTLポリシーも自動では戻りません。[3] PITRも過去7日、分単位の復旧であり、初期状態では直ちに7日前まで遡れるわけではありません。[4] つまり「バックアップがあるので大丈夫」は誤りです。

より重要なのは、復旧時点より後にStripe・Beds24・メールがすでに外部で実行されていることです。古いFirestoreを正として復帰させると、`AUTHORIZED`、未送信メール、未処理キューが過去に戻り、外部操作を再実行する危険があります。

**必要なBCP設計:**

1. **RTO/RPOを予約業務として定義**します。例として、閲覧停止・新規予約停止・既存予約参照・取消受付を別々に定義します。
2. 復旧中は全外部副作用ジョブを一斉停止する**kill switch**を持ちます。Firestore復元は、これを有効にしてから行います。
3. 新DBには直結せず、Stripe／Beds24から指定期間の予約・決済を再照合して、**復旧差分をappend-onlyで取り込む**手順にします。
4. TTL、IAM、インデックス、Security Rules、Secret参照、キュー、監視、同意／名簿の分離設定をIaCまたは復旧チェックリストで再適用します。
5. 四半期に一度、テスト環境で「本番相当バックアップ→新DB→外部照合→限定復帰」を演習します。

### 2.2 単一リージョン障害と外部障害の「購入継続策」がない

`asia-northeast1` に統一する判断はレイテンシ・簡潔性の点では妥当です。ただし同リージョン、Firebase Auth、Stripe、Beds24、DNS、メールのどれか一つが止まれば、通常フローは止まります。P1でマルチリージョン化を要求するのではなく、**安全に売らない／安全に代替する**方針を決めるべきです。

| 障害 | 安全な挙動 | あらかじめ準備するもの |
|---|---|---|
| 自社予約API／Firestore停止 | 新規の自社決済を停止。予約状況を約束しない | 静的障害ページ、既存のBeds24予約導線へのフェイルオーバー、切替権限 |
| Beds24停止・高遅延 | キャッシュ空室を販売根拠にしない。直販購入を停止 | 「空室確認中」表示、待機・問い合わせ導線、障害判断基準 |
| Stripe障害 | 予約作成も停止し、カード情報の再入力を誘導しない | Stripe Status監視、顧客向け文言、未確定Intentの再開手順 |
| メール障害 | 予約を無効化しない。問い合わせ／確認画面で再取得可能にする | メール送信キュー、配信状態、再送・代替通知手順 |

重要なのは、フェイルオーバー先で販売した予約を、復旧後に二重取り込みしないことです。切替には**開始時刻・終了時刻・予約経路・照合手順**を残します。

## 3. 設定変更と供給網 — コード外で壊れる領域

### 3.1 本当の本番設定は、リポジトリの外にある

仕様書はコードをよく見ていますが、予約商品の実体は次の管理画面設定にもあります。

- Beds24の部屋・offer・料金ルール・最小泊数・取消規約・Auto Actions・Webhook・ユーザー権限
- Stripeの支払手段、Radarルール、Webhook endpoint、返金権限、領収書・明細表記、3DS設定
- Firebase／Google CloudのIAM、Secret版、Security Rules、App Check、CORS、DNS、メール送信ドメイン
- GTM／GA4／広告のCV定義、同意設定、翻訳・規約・FAQコンテンツ

このどれかを管理画面で変更すると、アプリをデプロイせずに価格、決済可否、メール、個人情報、計測が壊れます。したがって、**「設定もプロダクトである」**と扱う必要があります。

| 統制 | 最低限の実装 |
|---|---|
| 設定台帳 | 設定項目、現在値、所有者、変更権限、依存先、ロールバック方法を一覧化する。 |
| 変更管理 | 料金・規約・Webhook・支払手段・権限変更は、二者レビューとチケット、適用日時、差戻し手順を必須にする。 |
| ドリフト検知 | 重要なBeds24／Stripe設定を日次スナップショットし、許可のない差分をアラートする。トークン・秘密は記録しない。 |
| 契約テスト | 本番に近い検証環境で、B24 offer→quote→作成、Stripeの状態遷移、メールテンプレート変数を毎日またはリリース時に自動検証する。 |
| 供給網対策 | lockfile固定、依存脆弱性監視、secret scan、CI/CDの最小権限、productionデプロイの承認と監査を導入する。 |

## 4. 金銭と会計 — 「決済成功」は入金・売上・返金完了ではない

### 4.1 予約台帳と会計台帳を混同していると月次で破綻する

予約の `total`、StripeのPaymentIntent、Charge、Refund、Dispute、Payout、Beds24の請求書、宿泊税、クーポン、チャージバック、外貨概算は、すべて金額・タイミング・状態が異なります。`bookings`コレクションを会計の唯一帳簿にしてはいけません。

**追加すべきものは「不変の金銭サブレジャー」と定例照合です。** 予約ごとに、内部予約ID、Beds24 ID、Stripe PaymentIntent／Charge／Refund／Dispute ID、通貨、税込／税抜、宿泊税、クーポン負担者、決済手数料、capture日、返金日、payout日、差異理由をイベントとして記録します。

| 照合頻度 | 照合対象 | 未一致時の扱い |
|---|---|---|
| 毎日 | confirmed予約 ↔ Stripe capture ↔ Beds24予約 | 新規の差異は販売停止ではなく例外キュー。ただし未収予約は即時有人対応。 |
| 毎日 | Stripe refund／dispute ↔ Beds24取消 ↔ 顧客通知 | 金額または状態が不一致なら自動再実行せず、担当者が証憑を確認。 |
| 月次 | Stripe payout・手数料・返金 ↔ 会計仕訳 ↔ 予約売上 | FinanceとAccountantが別責任でレビューし、締め後訂正は調整仕訳として残す。 |

外貨の「概算」も、顧客向け表示としては問題になり得ます。レート供給元、取得時刻、キャッシュ期間、通貨ごとの丸め、障害時の非表示化、JPY請求額との乖離説明を記録してください。概算レートを予約台帳の会計金額に使うことは厳禁です。

## 5. 人・物理運用 — アプリ外の当日失敗が最も顧客体験を壊す

### 5.1 「予約確定」後の失敗を、予約システムの対象に含める

高品質な予約処理でも、当日以下が失敗すれば顧客には「予約が失敗した」と同じです。

| 当日シナリオ | 現行設計に潜む穴 | 必要な対策 |
|---|---|---|
| 鍵／入室案内未達 | 3日前メールだけに依存すると、迷惑メール・住所不備・通信不能で詰む | 本人認証済み `/account` で再表示、配信監視、緊急連絡先、送付／再送の証跡、運営の当日対応SLAを定義。 |
| 到着予定未回答 | リンクがGoogleログイン必須なら、予約者と代表宿泊者が異なる場合に回答できない | 予約者・代表者・現場の権限を分ける。メールのトークンURLを使うなら、短寿命・一回利用・目的限定・Referer漏えい対策・再認証条件を設計。 |
| 自然災害・交通遮断・設備故障 | 取消規約の通常パスだけでは判断できない | force majeure、代替宿泊、部分返金、無償取消、現場判断上限、顧客への一斉連絡と決裁者をRunbook化。 |
| 人数超過・本人不一致・ルール違反 | 決済時の同意だけでは現場が判断できない | 予約情報、同意版、名簿、証拠写真等の扱いを分離し、現場が取れる措置・警察連絡・返金可否・エスカレーションを合意する。 |
| 緊急連絡 | `contact@mail` 転送は24時間の緊急対応手段ではない | 電話／一次窓口、言語別案内、応答責任者、営業時間外の自動案内を明示する。 |

### 5.2 役割分担はRACIだけでなく「不在時」に耐える必要がある

オーナー、運営会社、開発者、経理担当の全員が、旅行・病気・退職・権限剥奪で不在になる前提にします。特に返金、個人情報事故、Stripe紛争、緊急入室対応は、**担当者が一人しかいない状態を禁止**してください。

推奨は、通常権限を最小化しつつ、緊急時だけ時間制限つきで昇格する**break-glass権限**です。実行者・理由・承認者・期限・操作結果は監査ログに残し、翌営業日に必ずレビューします。

## 6. セキュリティ・プライバシーの二次被害

### 6.1 正規のメールリンクとURLパラメータが情報流出経路になる

URLで予約状態を復元する設計は便利ですが、URLはブラウザ履歴、スクリーンショット、アクセスログ、Referer、外部ブラウザへの共有で露出します。ここに `quoteId`、予約ID、長寿命の認可トークン、メールアドレス、氏名を入れると、攻撃者が予約照会や操作をできるおそれがあります。

**原則:** URLに保持してよいのは、棟・日付・人数・言語などの非機微な選択値だけです。予約参照・到着時刻更新・取消操作は、認証済みセッションまたは短寿命・目的限定・一回利用の署名付きトークンを使い、トークンをログ・分析・外部リンク・Refererへ出さない設計にします。メールリンクを踏んだだけで取消・同意変更などの副作用を実行してはなりません。

### 6.2 バックアップ・分析・サポートツールが最終的な漏えい面になる

予約本体を堅くしても、バックアップ、Firestore復旧DB、ログ、GA4/GTM、メール送信ログ、障害チケット、CSVエクスポートにPIIが残れば、実効的な漏えい面は広がります。PPCは、一定の漏えい等では本人通知と報告を求め、速報は概ね3〜5日、確報は原則30日以内（不正目的のおそれがある場合60日以内）と案内しています。[5]

| 管理対象 | 深層要件 |
|---|---|
| ログ・分析 | メール、電話、氏名、住所、パスポート、決済IDを原則出力しない。トレースIDで結合し、閲覧者を限定する。 |
| バックアップ／復元DB | 本番と同等のIAM・暗号化・監査を適用し、復元検証後は削除する。TTLが自動復元されない点も復旧手順に含める。[3] |
| CSV・管理画面 | ダウンロードの目的・範囲・有効期限・透かし・操作ログを持たせる。名簿と旅券は通常のCSV出力対象外。 |
| インシデント対応 | 事実確認、封じ込め、証拠保全、連絡先、通知文、PPC報告、委託先連絡、再発防止の責任者を事前指定する。 |
| 委託先 | Beds24、Stripe、Firebase／Google、メール、運営会社のデータフロー・再委託・国外処理・事故通知を、契約・プライバシー通知・台帳で矛盾なく管理する。 |

### 6.3 不正利用は「カード試行」だけではない

App Check、レート制限、Radarを入れても、次の業務不正は残ります。

- クーポンを多重利用するための複数Googleアカウント作成
- 高需要日に、決済意思のない予約を繰り返して在庫を一時拘束する行為
- 本人のGoogleログイン済み端末を使った家族・共有端末からの取消
- 運営者権限での不正返金、名簿の持出し、料金ルールの操作
- 請求者・予約者・実宿泊者の不一致を悪用したチャージバック

対策は一律のブロックではなく、**予約・顧客・支払・端末・運営操作のリスク信号を分離**して、追加本人確認、手動レビュー、購入制限、返金二者承認を段階的に適用することです。国籍や言語を不正判定の代理変数に使わないこともルールにしてください。

## 7. 品質保証・計測・組織学習の穴

### 7.1 テストは仕様試験から「不変条件試験」へ進める

ケース列挙だけでは、組合せ爆発を防げません。次の不変条件を自動テスト／監視にします。

| 不変条件 | 常時検証する内容 |
|---|---|
| 金銭 | `capture済み額 − refund済み額` と予約の請求確定額が許容差0で一致する。 |
| 在庫 | `CONFIRMED` な直販予約はBeds24に一件だけ存在し、同じ部屋・泊日に許容量超の確定予約がない。 |
| 通知 | 「予約確定」通知は、Beds24確定・Stripe確定・規約版保存の三条件を満たす時だけ一回送る。 |
| 権限 | 利用者は自分の予約のみ読み書きでき、管理操作はすべて実行者・理由・承認と結び付く。 |
| 時間 | 無償取消判定は物件タイムゾーンと予約時保存のpolicy versionで再現できる。 |
| 復旧 | どの段階で停止しても、再実行は外部操作を増やさず、最終的に定義済みの一状態へ収束する。 |

広告切替、連休、クーポン配布の前には、負荷試験だけでなく、**障害注入（Beds24 429／timeout、Stripe webhook再送、メール不達、Firestore一時エラー、設定変更）**を行うべきです。ここで初めて、Runbookと当番が実用に耐えるか分かります。

### 7.2 計測が止まっても、経営判断が止まらないようにする

同意拒否、広告ブロッカー、WebView、Safari制約、クロスデバイスによりGA4／広告のCVは欠落・重複し得ます。**広告管理画面のCVを売上の真実にしてはいけません。**

Stripe・Beds24・自社金銭台帳を基にした日次の予約・純売上集計を経営KPIの正とし、GA4／広告はファネル改善と施策比較の補助指標として扱います。GA4、広告、内部台帳の差異率を定期的に出し、いつ数字を信用できないかを経営会議で共有してください。

## 最終チェック — 本番責任者に問う10問

以下に一つでも「担当者が口頭で知っているだけ」の項目があれば、まだ設計穴です。

1. 24時間後に古い予約作成タスクが届いても、取消済み予約を復活させないことをどの自動試験で証明するか。
2. Beds24、Stripe、自社の各属性で、差異時に誰がどちらを正として修正するか。
3. Firestoreを昨日の状態へ復旧した直後、外部操作を再発させずに今日のStripe／Beds24と再整合する手順は何か。
4. Beds24で人が料金・規約・取消・Auto Actionsを変更したことを、いつ、誰が検知するか。
5. 新規予約を安全に停止しつつ、既存予約者を迷わせずに案内する障害ページと切替権限はあるか。
6. Stripeの決済成功、返金、dispute、payoutを会計上どのIDとどの月次手順で照合するか。
7. 到着案内メールを受け取れない顧客を、当日誰がどの言語で救済するか。
8. URL、ログ、バックアップ、分析、CSVに、予約参照や個人情報に使える秘密が漏れないと何で保証するか。
9. 管理者・運営担当が不在または侵害されたとき、誰が緊急権限を取得し、翌日に誰がレビューするか。
10. 予約を止めるべき異常（整合差異、返金失敗、Webhook遅延、名簿未回収、メール障害）を、誰が何分以内に判断するか。

## 結論

全改善を反映した後のP1に対して、私は**「実装可能」ではなく「運用可能性の実証に進める段階」**と評価します。最後に残る競争力は、画面の完成度ではなく、**設定変更、再実行、復旧、会計、現場例外を可視化して制御できる能力**です。

最優先で追加するなら、次の三つです。

1. **属性別SSOT＋外部操作台帳＋状態version**を仕様・実装・監視に通すこと。
2. **復旧時の副作用停止と外部再照合Runbook**を作り、復元演習をすること。
3. **金銭サブレジャーと設定ドリフト検知**をP1の範囲へ入れること。

これらを入れると、単に「予約が通る」システムから、障害・人の変更・月次締めにも耐える**事業運営基盤**へ格上げされます。
