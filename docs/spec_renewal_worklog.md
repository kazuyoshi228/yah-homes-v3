# 仕様書 — 更新計画と作業台帳の切り分け（消し込み・アラート）

- 状態: **承認済み・実装済み（2026-08-24）**
- 起票: 2026-08-24
- きっかけ: 「設備台帳とどう切り分けていく？タイムライン付きで更新作業が発生するものを作業台帳にする？消し込みをできる機能を追加する。定期的にアラートする」（発注者）

---

## 1. 結論 — 作業台帳は新設しない

**既に同じものがある。** 外部委託のために作った `schedules`（周期マスタ）→ `jobs`（ジョブ）→ 状態遷移
（draft / sent / negotiating / confirmed / done / verified）→ `scheduleNext`（完了したら次回を自動登録）が、
そのまま「タイムライン付きの作業台帳・消し込み・アラート」です。毎朝の Cloud Scheduler で起票と警報も動いています。

足りないのは**接続**であって、器ではありません。器をもう一つ作ると、更新の予定が2か所に載って必ずズレます。

---

## 2. 3層の役割（どれが何の正本か）

| 層 | コレクション | 正本にしているもの | 画面 |
|---|---|---|---|
| **物の台帳** | `equipment` | 何が・いくらで・何年もつか（`amount` `installedAt` `lifespanYears`） | 物件カードの各タブ |
| **予定** | `schedules` | いつやるか（周期・月・前倒し日数・業者） | Agency > 定期メンテナンス |
| **実績** | `jobs` | やったか・いくらだったか・誰が（timeline は追記のみ） | 物件カード > 作業／Agency > 定期メンテナンス |

更新計画（物件カード）と設備台帳（運営）は、**この3つを読んで並べるだけの面**です。作業を起こしません。

- **物件カード > 更新計画** … 1棟のなかの計画。積立が足りているかを判定する
- **運営 > 設備台帳** … 全棟横断。年の山が重なっていないかを見る
- **Agency > 定期メンテナンス** … 全棟の待ち行列。今日やること・依頼・承認
- **物件カード > 作業** … その棟の履歴と消し込み

消し込みのボタンは両方にあってよい。**SSoTは「入力口が1つ」ではなく「保存先が1つ」**で、
どちらも同じ `jobs` に同じ `advance()` で書くため。洗濯機で起きた問題は保存先が2つ
（追加投資額の配列と設備台帳）あったことで、ボタンの数ではなかった。

ただし**依頼メールの送信と承認は横断側にだけ置く**。業者とのやりとりは棟をまたぐのと、
承認は人だけの操作として1か所に集めておきたいため。

---

## 3. 消し込みで何が動くか（ここが肝）

ジョブを `verified` にしたとき、紐づく設備台帳の項目へ**書き戻す**。

```
jobs.verified
  ├→ equipment.installedAt = 実施年月        … 次の更新年が自動でずれる
  ├→ equipment.amount      = 実額（請求額）   … 概算が実額に置き換わる＝年割りが本物になる
  ├→ equipment.estimate    = 削除            … 「概算」バッジが消える
  ├→ equipment.history[]   に1行追記         … 何年に・いくらで・どの業者か（追記のみ）
  └→ scheduleNext()        で次回ジョブを登録  … 既存の仕組みがそのまま働く
```

これで**消し込むたびに更新計画が実額に近づきます**。いま概算9件で¥216,501/年としている長期修繕が、
1回目の実施で実額に置き換わり、積立額の妥当性の判定が推測から実績に変わる。

紐づけは既に入れた `schedules.ledgerId`（→ `equipment` のドキュメントID）を使います。
`ledgerId` が無いジョブは、これまでどおり書き戻しをしません（清掃・消防点検など、物に紐づかない作業）。

## 4. どの項目を作業にするか

**63件すべてを作業にしない。** LED電球¥8,650に発注ジョブを立てても運用が回らなくなります。

台帳の項目に `workOrder: true` を持たせ、これが立っているものだけ `schedules` を持ちます。

初期の基準（提案）:

| 条件 | 例 | 作業化 |
|---|---|---|
| 金額 ¥100,000 以上 | 防水・外壁塗装、屋根、給湯器、洗濯機 | ○ |
| 法令で義務 | 住宅用火災警報器、24時間換気 | ○（金額に関わらず） |
| 建物の維持に関わる | シロアリ防除、給排水管、FRP防水 | ○ |
| 上記以外 | LED電球、額縁、スイッチプレート | ×（更新計画に金額として残るだけ） |

いまの清川なら**11件**が作業化の対象（長期修繕9件＋洗濯機＋エアコン4台をまとめて1件）。
残り52件は年割りの計算に入るだけで、ジョブは立ちません。

## 5. アラート

既存の `alerts.ts` と毎朝の起票にそのまま乗せます。**新しい通知経路は作りません。**

| 何を | いつ | どこへ |
|---|---|---|
| 更新期が来る | `schedules.leadDays` 前（長期修繕は120日、機器は60日） | 定期メンテナンスに `draft` で起票 |
| 見積が概算のまま | 実施年の**1年前** | 「見積を取る」ジョブを起票 |
| 期日を過ぎても未着手 | 期日の翌月 | 既存の `findOverdue` の警報に乗る |
| 積立が年割りを下回った | 月次の締めのとき | 固定費カードに⚠（既にある判定を警報に格上げ） |

**fail-closed の原則は既存のまま。** 業者が未定・金額が概算のジョブは `needsDecision: true` で、
AIは依頼メールを出しません。人が業者を決めて `active` にするまで動かない。

---

## 6. 画面に足すもの

| 画面 | 足すもの |
|---|---|
| 物件カード > 更新計画 | 各行に「作業」列。ジョブがあれば状態、対象なら「未起票」、対象外は「—」 |
| 物件カード > 作業（新設） | その棟のジョブを時系列で。実額と実施年月を入れて消し込む |
| 運営 > 設備台帳 | 更新カレンダーの各年に、ジョブの有無を出す。実施済みの年は取り消し線 |
| Agency > 定期メンテナンス | 完了時に**実額と実施年月を入れる欄**（これが書き戻しの入力口） |

---

## 7. やらないこと

- **作業台帳という新しいカードは作らない。** 横断は Agency > 定期メンテナンス、棟ごとは物件カードのタブ
- **実績金額を equipment とは別に持たない。** 持つと必ずズレる。`amount` を上書きし、`history[]` に前の値を残す
- **AIに完了を判断させない。** `verified` は人だけ（既存の鉄則のまま）

## 8. 実装の順（承認後）

1. `equipment.workOrder` を11件に立てる（データのみ・画面は変わらない）
2. `jobs.verified` → `equipment` 書き戻し（`ledgerId` 経由）＋ `history[]`
3. 定期メンテナンスの完了欄に「実額・実施年月」を追加
4. 更新計画・設備台帳に「作業」列
5. 見積アラート（実施年の1年前）を `alerts.ts` に追加
