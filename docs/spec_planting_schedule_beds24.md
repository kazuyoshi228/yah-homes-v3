# 仕様書 — 植栽メンテの記録と、業者向け「作業に入れる日」カレンダー（Beds24連携）

- 状態: **実装済み・本番稼働（2026-08-25 発注者承認）**。E2E検証済み（選択→二重選択409→報告→通知→取消で空きに復帰）。§2-1の周期投入のみ台帳待ち
- 起票: 2026-08-25
- きっかけ: 「植栽メンテのスケジュールを記録していきたい。Beds24のAPIと連携して、
  植栽メンテに入ることが可能な日程を業者がわかるためのツールも実装したい」（発注者）
- 担当カード: 植栽メンテ（planting.html）＋ functions は新設1本のみ

## 0. 結論（先に要点）

1. **記録は新しい器もUIも作らない。** 既存の schedules（周期）→ jobs（実施・消し込み）に
   区分「植栽」で乗せ、入力はメンテナンスカードの既存の完了欄・突発ジョブをそのまま使う
   （2026-08-25 発注者決定）。植栽カードは読み取り表示のまま
2. **空き日カレンダーは「トークン付きの公開ページ」1枚。** 業者はログイン不要でURLを開くだけ。
   **チェックアウト日（11:00〜15:00）だけを「入れる日」として表示**し、
   選択→作業→完了報告まで同じページで完結する
3. データ源はBeds24の予約API。**1時間キャッシュ**でBeds24を叩きすぎない。
   落ちていたら最後に取れた断面を「◯時間前の状態」と明示して出す（fail-soft）

## 1. いまある器（作らないものを先に）

| 器 | 現状 | この仕様での扱い |
|---|---|---|
| `schedules` | 周期マスタ（区分・月・棟・業者・active/needsDecision） | **そのまま使う**（区分=植栽） |
| `jobs` | 起票→依頼→完了→検収の状態遷移・timeline追記 | **そのまま使う**（消し込み） |
| 植栽メンテカード | 台帳（plants）＋区分=植栽の予定・履歴を表示 | 読み取りのまま（記録はメンテナンスカードで） |
| Beds24観測 | 毎朝8:00にカレンダーをGCSへ保存（クラウド定点） | 使わない（後述※） |
| `BEDS24_WRITE_REFRESH` | Secret Managerにトークンあり（accountApiが使用中） | **読み取りで再利用** |

※毎朝の観測データを使えばBeds24を叩かずに済むが、更新が1日1回＝当日の新規予約を拾えない。
庭作業は「入ってみたらゲストがいた」が一番の事故なので、**表示のたびに新鮮な断面**（1時間キャッシュ）を採る。

## 2. A. スケジュールの記録

### 2-1. 周期（例・承認後に初期データとして投入）

| 棟 | 作業 | 月 | 状態 |
|---|---|---|---|
| 清川 | 剪定・除草 | 6月・11月 | **無効（needsDecision）**＝業者が決まるまでAIは動かない |

※対象は当面**清川のみ**（2026-08-25 発注者決定）。高砂以降は植栽が台帳に載ったら追加

- 月・回数は台帳（plants）が埋まってから確定する。**樹種が分からないまま周期は決められない**
- fail-closed の原則は既存のまま。業者を決めて active にするまで依頼メールは出ない

### 2-2. 実施の記録（消し込み）— メンテナンスカードに集約（2026-08-25 発注者決定）

**植栽カードに記録UIは作らない。** メンテナンスカードには完了欄（実施日・実額）も
突発ジョブのボタンも既にあり、区分「植栽」のジョブをそのまま扱える。同じUIをもう1組
作るのは複製で、今日のP5で消した種類の重複を自分で増やすことになる。

- 記録＝メンテナンスカードの既存の消し込み（done→verified・scheduleNext が次回を自動起票）
- 突発（台風後の枝処理など）＝メンテナンスカードの既存の突発ジョブ
- 植栽カード側は予定・履歴の**読み取り表示のまま**＋「記録はメンテナンスで」リンクを1つ置く

台帳（plants）との紐づけは**しない**（木1本ごとにジョブを割ると運用が回らない。
作業は「棟×回」の粒度で記録し、どの木をやったかはジョブのメモに書く）。

## 3. B. 業者向け「作業に入れる日」カレンダー

### 3-1. 判定のルール（2026-08-25 発注者決定で全面差し替え）

**作業可能日＝チェックアウト日のみ。作業時間は 11:00〜15:00 固定。**

| 表示 | 判定 |
|---|---|
| **○ この日入れます（11:00〜15:00）** | Beds24の確定予約がその朝チェックアウトする日 |
| （表示しない） | それ以外すべて（滞在中・完全空室日も出さない） |

チェックアウト日に絞る理由（完全空室日を出さない理由）:
1. **後から予約が入っても窓が壊れない。** 完全空室日は販売中の在庫で、業者が選んだ後に
   予約が入ると作業日が潰れる。チェックアウト日の11〜15時は「確定済みの退去」と
   「16時チェックイン」に挟まれた窓なので、当日に新規予約が入っても影響しない
2. 判定が単純＝事故らない。◎△×の3段階より「○の日だけ出す」が業者にも伝わる
3. 鍵・立ち会いの段取りが清掃と同じリズムに乗る

- 表示期間: 今日から90日先
- 注意: 同じ時間帯に清掃（Airstar）が入る。庭は屋外作業なので併存できる想定だが、
  業者への注意書きに「清掃スタッフが在室の場合あり」と明記する

### 3-1-2. 流れ（表示 → 選択 → 作業 → 報告）

```
① 業者がトークンURLを開く → ○の日が並ぶ
② 日を選んで「この日に入ります」を送信
     → ジョブ作成（区分=植栽・日付き・confirmed）＋選ばれた日は以後「選択済み」表示
     → オーナーへ通知メール（既存の警報経路。承認待ちにはしない——
        窓が予約に壊されない設計なので、自動確定＋オーナーは取消できる、で回す）
③ 当日 11:00〜15:00 に作業
④ 完了報告（§3-4）→ done → オーナーが検収（verified・人だけ）
```

### 3-2. 業者への見せ方 — トークン付き公開ページ

```
https://os.yah.homes/niwa/{token}     ← ログイン不要・このURLを業者にLINEで送るだけ
```

- 中身: 清川の月カレンダー（○の日のみ）＋注意書き
  （「予約は毎時更新・作業日が決まったら山田へ連絡→仮押さえ」）
- **出さないもの**: ゲスト名・人数・金額・予約経路。出すのは◎△×だけ
  （空室情報自体はAirbnbの公開カレンダーで誰でも見られるため、開示リスクは増えない）
- トークンは32文字ランダム・Firestore `settings/planting` に保存・**いつでも無効化できる**
  （業者を替えたらトークンを作り直す）。noindex・robots拒否
- スマホ最適化必須（業者は現場のスマホで見る）——このページだけはモバイルファースト

### 3-3. 実装の形

```
functions:  plantingCalendar (onRequest・公開・トークン必須)
  ├ settings/planting.token と照合（不一致は404。存在を教えない）
  ├ Beds24 getBookings（清川のみ・今日〜+90日）※2026-08-25 発注者決定。高砂以降は必要になったら足す
  ├ キャッシュ: Firestore beds24cache/planting に1時間（Beds24のレート節約）
  └ 返すのは {prop: {date: "◎|△|×"}} だけ。予約の中身はサーバから出さない

hosting:    niwa.html（公開・軽量1枚。os.cssは使わない＝ログインUI一切なし）
rewrite:    /niwa/** → plantingCalendar は使わず、niwa.html?t={token} が関数を叩く
```

- Beds24が落ちている/レート超過のとき: 最後のキャッシュを「◯時間前の状態です」と明示して表示。
  キャッシュも無ければ「表示できません。山田へ連絡してください」（誤った◎を出すくらいなら出さない）
- オーナー側: 植栽メンテカードに同じカレンダーを埋め込み表示＋「業者用URLをコピー」「トークン再発行」

### 3-4. C. 業者の完了報告（2026-08-25 発注者追加）

業者がトークンページから**自分で「作業完了」を報告できる**ようにする。

```
niwa.html に「作業完了の報告」フォーム:
  日付・棟・作業内容（自由記述）・かかった金額（任意）・写真（任意・5枚まで）
      ↓ plantingCalendar 関数の POST（同じトークンで認証）
  開いているジョブ（区分=植栽・該当棟）があれば → そのジョブを done へ・timelineに「業者報告」
  無ければ → 突発ジョブを vendorReported=true で新規作成（done 状態）
  写真 → 保管庫 reports/planting-work/{年月}/ へ保存しジョブに紐づけ
      ↓
  オーナーへ通知メール（既存の警報経路に乗せる。新しい通知経路は作らない）
```

**鉄則は変えない: `verified`（検収・消し込みの確定）は人だけ。**
業者報告は done 止まりで、実施日・実額の確定と台帳への書き戻しは、これまで通り
オーナーがメンテナンスカードで検収したときに走る。写真があれば現地に行かずに検収できる——
ここがこの機能の実利（報告→写真確認→検収まで、現地確認ゼロ・LINEゼロ）。

セキュリティの割り切り:
- 書けるのは「区分=植栽のジョブのdone報告」と「vendorReported付き突発ジョブの新規」だけ。
  それ以外のコレクション・状態には一切触れない
- トークン漏れ時の被害＝偽の報告が入る、まで（検収は人なので誤消し込みは起きない）。
  報告はレート制限（1時間10件）・写真は5MB×5枚まで・トークン再発行でいつでも遮断
- 日付の選択は本編に昇格（§3-1-2）。フェーズ2に残るのは「複数日の一括申請」など運用で必要になったら

## 4. やらないこと

- **植栽専用のスケジューラ**（schedules/jobsで足りる。二重の予定表は必ずズレる）
- **木1本単位のジョブ**（粒度が細かすぎて回らない。棟×回で記録）
- **Beds24への書き込み**（ブロック作成など）。読み取り専用。作業日の確定は人がやる
- **業者アカウント・ログイン**（トークンURLで足りる。管理が増えるだけ）
