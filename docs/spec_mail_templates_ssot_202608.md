# 仕様書：定型メールのSSoT化（B案）

作成 2026-08-10 / 対象 yah.homes 直販P1 / 状態 **実装済み（2026-08-18 状態行を実態に同期）

## 1. なぜやるか

いま `/admin/templates` は「唯一の正」と称しているが、**送信されるメールを一切支配していない**。
自動送信はコード内の `MAIL_L10N` / `LIFECYCLE_L10N` を読んでおり、画面で文面を直しても
届くメールは変わらない。手動送信だった頃は「運営が見てコピーする台本」として機能していたが、
全自動化した時点でこの画面は**実物と同期しない写し**になった。

さらに、実際は5言語（ja/en/ko/zh/th）で送っているのに、画面には ja/en の8本しかない。
**韓国語・繁体字・タイ語の文面は画面から確認も編集もできない。**

```
実際に送っている   4通 × 5言語 = 20
画面に載っている   4通 × 2言語 =  8   ← 12本が不可視
```

この2つを同時に解消する。

## 2. やらないこと（重要）

**HTMLの構造・レイアウトは編集対象にしない。** 編集できるのは文言だけ。

編集者にHTMLを触らせると、メールクライアント互換（table+インラインCSS）が
一度の編集で壊れる。予約番号の表・料金の表・ボタンは、値も配置もコードが持つ。
テンプレートが差し替えるのは、そこに流し込まれる**文字列だけ**。

## 3. 方式：文言キーの上書き

テンプレート1件 = 「その通・その言語の文言キーを上書きする辞書」。

```
mail_templates/{kind}_{lang}
  kind : confirm | checkin | checkout | review
  lang : ja | en | ko | zh | th        → 全20件
  strings: { [key: string]: string }   ← 上書きしたいキーだけ持つ
  title, order, updatedAt, updatedBy
```

送信時は `コード既定 → strings で上書き` の順にマージする。

```ts
const L = { ...CODE_DEFAULT[lang], ...(await loadTemplate(kind, lang))?.strings };
```

**この方式を選ぶ理由**は3つ。

1. **落ちない。** キーが無ければコード既定が出る。テンプレートが消えても、
   1キーだけ空でも、メールは必ず送れる。文面の編集ミスで送信が止まる事故が起きない。
2. **レイアウトが壊れない。** 上書きできるのは文字列だけなので、
   どう編集してもHTMLの骨格は変わらない。
3. **移行が無変化。** 初期投入をコード既定と同一の値にすれば、
   切り替え当日にお客様へ届くメールは1文字も変わらない。

### 編集できるキー（例：チェックイン案内）

| 画面のラベル | キー | 現在の値（ja） |
|---|---|---|
| 件名 | `remSubject` | 【yah.homes】明日のご宿泊について |
| 見出し | `remHeading` | 明日、お待ちしております |
| 書き出し | `remLead` | ご到着が明日となりました。… |
| 入室について・本文 | `remEntryBody` | 玄関のキーボックスでの受け渡しです。… |
| 到着時刻の注記 | `remArrivalNote` | 到着時刻に制限はありません。… |
| ボタンの文字 | `remCta` | 予約を確認する |

4通あわせて編集対象は **ja で32キー**、5言語で160キー。
画面ではラベル付きの入力欄として並べる（1本の巨大なテキストエリアにはしない）。

## 4. 差し込み記号

現状の差し込みは**コードが値を埋めている**（`{ci}` `{n}` `{d}` など）。
テンプレート側でも同じ記号を使えるようにし、送信時に置換する。

| 記号 | 出所 |
|---|---|
| `{{guestName}}` `{{guests}}` `{{nights}}` `{{checkin}}` `{{checkout}}` | 予約ドキュメント |
| `{{propertyName}}` `{{checkinTime}}` `{{checkoutTime}}` | `property_facts` |
| `{{manualUrl}}` `{{mapUrl}}` `{{registerUrl}}` `{{phone}}` | 物件ファクト |
| `{{keyboxCode}}` | `property_secrets`（オーナー専用コレクション） |
| `{{bookingNo}}` `{{myPageUrl}}` `{{registerDeadline}}` | 送信時に算出 |

**未知の記号は空文字にして送る**（`{{typo}}` がそのままお客様に届かないようにする）。
同時に `logger.warn` を出す。保存時にも未知の記号を弾いて画面に警告を出す。

## 5. 読み込みとキャッシュ

- 送信のたびに Firestore を1回読む（`mail_templates` を kind+lang で1件）。
  スケジューラは1日数十通なので、コスト・遅延とも無視できる。
- **読み込みに失敗したらコード既定で送る。** Firestoreの一時障害でメールを止めない。

## 6. 画面（/admin/templates）

- サイドバーを **通（4）× 言語（5）** に組み替える。言語はタブで切り替える。
- 各キーは「ラベル・入力欄・既定値の表示・〈既定に戻す〉」の4点セット。
  **いま既定と違う値になっているキーには印を付ける。** どこを触ったか一目で分かるようにする。
- **テスト送信**：自分宛に1通送るボタン。ダミーの予約データで差し込みを展開する。
  実際に届くものを見ずに本番の文面を変えさせない。
- 権限は現行どおり管理者台帳のメンバー。変更は `audit_logs` に残す。

## 7. 移行手順

1. コード既定を全20件・全キー分そのまま Firestore へ投入する（`seed-mail-templates.mjs`）。
2. 投入後、既定とテンプレートの差分が **0件** であることをスクリプトで照合する。
3. 送信側をマージ方式に切り替える。
4. 各通1回ずつテスト送信し、切替前後で本文が同一であることを確認する。
5. 旧テンプレート8件（`confirm_ja` 等の body 形式）は削除する。

## 8. 受け入れ条件

- [ ] 4通 × 5言語 = 20件が画面に並び、すべて編集できる
- [ ] 画面で文言を変えると、次の送信に反映される
- [ ] テンプレートを削除しても、キーを空にしても、メールは既定文言で送れる
- [ ] Firestoreが読めないときも既定文言で送れる
- [ ] 未知の差し込み記号がお客様に届かない
- [ ] 移行直後、送信されるメールが切替前と1文字も変わらない
- [ ] テスト送信で実物を確認できる
