## 結論

本設計の**経営・プロダクト方針は正しい**です。Beds24 を在庫・料金・OTA同期の基幹として残し、自社側を体験・決済・CRM・計測に限定する判断は、P1でフルスクラッチのPMSを作るより遥かに合理的です。また、価格の後出しを避け、取消期限を実日付で示し、チェックアウトでハウスルールと販促同意を分ける方針も、直販転換と紛争予防の両面で良い出発点です。

ただし、**「Beds24への予約作成」と「Stripeのオーソリ／売上確定」をまたぐ分散トランザクション**が、現状は業務フローとして記述されているだけで、障害時に正しい最終状態へ収束する設計になっていません。予約APIのタイムアウト、Beds24作成成功後のStripe capture失敗、Webhook重複・順不同、取消途中失敗のいずれでも、未収予約、二重予約、二重返金、あるいは顧客に沈黙する状態が起こり得ます。

したがって、本書は「設計確定・実装前」ではなく、**「アーキテクチャ方針確定・詳細設計未完」**へステータスを戻すべきです。以下の **P0 を設計書に反映し、テストで実証すること**を MS3 の開始条件にしてください。

### 予約・決済の推奨状態遷移

> **原則:** Beds24とStripeの間に原子的コミットはないため、「一度のHTTPリクエスト内で完結させる」のではなく、障害から必ず収束できる**状態機械＋補償処理**として実装する必要があります。

| 状態 | 許容する次状態 | システムの行為 | 顧客への表示・運用 |
|---|---|---|---|
| `QUOTE_ISSUED` | `PAYMENT_PENDING` / `EXPIRED` | 料金・在庫スナップショットを署名付きで保存 | 「料金は確認時に再検証されます」 |
| `PAYMENT_PENDING` | `AUTHORIZED` / `PAYMENT_FAILED` | PaymentIntentを生成。クライアントは3DSを含め確認 | 未完了なら再試行可。予約確定とは表示しない。 |
| `AUTHORIZED` | `RESERVATION_HELD` / `VOIDED` | Webhookでオーソリ確認後、Beds24へ仮状態または予約作成 | 作成失敗ならPaymentIntentをcancelし、理由を通知 |
| `RESERVATION_HELD` | `CONFIRMED` / `CAPTURE_PENDING` / `CANCEL_PENDING` | captureを冪等実行。タイムアウトは再照会してから再試行 | 「予約処理中」。所定時間を超えたら有人通知 |
| `CONFIRMED` | `CANCEL_REQUESTED` | 決済・Beds24双方の確定を照合してから確認メール、GA4 purchase | 予約番号・規約版・取消期限を通知 |
| `CANCEL_REQUESTED` | `CANCELLED` / `MANUAL_REVIEW` | 取消・返金の非同期実行と照合 | 返金完了の見込みを明示し、失敗は沈黙させない |

## 4. 事業・運用設計への厳しいコメント

### 「運営会社の作業手順書に変更ゼロ」は、達成不可能な要件です

直販では、カード拒否、予約処理中、名簿未回収、取消例外、チャージバック、到着予定未回答、販売者への問い合わせが必ず発生します。通常運用をBeds24に寄せることは正しいですが、**例外業務までゼロにはできません**。ここを「変更ゼロ」と置くと、例外が現場に隠れ、最も忙しい当日に破綻します。

要件を次のように置き換えるべきです。

> **通常の予約確認・ゲストメッセージ対応は既存Beds24画面で完結する。直販固有の例外は、役割・判断上限・一次回答SLA・エスカレーション先を定めた1枚のRunbookで処理できる。**

また、`contact@mail.yah.homes` への転送は通知の受け皿に過ぎません。誰が24時間以内に見るのか、障害メールと顧客メールをどう分けるのか、迷惑メール化・転送失敗をどう監視するのかを決めなければ、運用要件として未完成です。

### KPIは「直販比率」だけでは操縦できません

12か月35%、18か月50%は経営目標としてよい一方、直販比率だけでは、OTA供給変化や稼働率の影響とプロダクトの効果を分離できません。「広告着地を自社予約へ +17〜25%」等の増分仮説にも、基準値・母数・期間・測定方法がありません。

| レイヤー | 経営が毎週見るべき指標 | 目的 |
|---|---|---|
| 収益 | 直販GBV、直販粗利、OTA対比の手数料削減、キャンセル後純売上 | 直販が本当に利益を増やすか確認する |
| ファネル | 物件閲覧→日付選択→棟選択→認証→決済開始→確定の転換率 | 離脱箇所と認証摩擦を特定する |
| 信頼性 | quote成功率、B24作成成功率、支払確定率、処理時間、整合差異件数 | 売上ロス・運用リスクを早期検知する |
| 顧客 | リピーター比率、同意率、クーポン利用率、再予約率、CS問い合わせ率 | CRM仮説を検証する |

「直販1予約あたり約¥15,000の手数料回収」は、物件別の平均客単価、OTA別手数料、決済・CRM・広告費、キャンセル率を含む**限界利益**で再計算してください。直販の価格を常に-2%にするなら、値引きと決済原価を控除した後もOTAよりどれだけ有利かを、物件・チャネル別に可視化する必要があります。

## 5. マイルストーンの再構成案

現行の期間見積りは、UI構築には近いものの、決済・多言語・連携・運用開始に必要な検証を織り込めていません。特にMS1「1〜3日で全チャネル予約がFirestoreに入る」とMS3「1〜2週で決済・予約・5言語メール」は、品質ゲートなしには楽観的です。人員構成と既存資産が不明なため工数は断定しませんが、**順番**は以下へ変更すべきです。

| ゲート | 完了物 | 次へ進む条件 |
|---|---|---|
| G0: 責任・規約確定 | 契約当事者、Merchant of Record、キャンセル規約、物件営業形態、個人情報台帳、運営RACI | 法務・運営・オーナーが文書承認 |
| G1: 連携スパイク | Beds24のpropid／room／offer／料金・Webhook・書込・取消・重複時の実機検証、Stripe test modeの状態遷移 | APIの不明点がテスト結果で閉じ、詳細設計を更新 |
| G2: 整合性基盤 | 状態機械、operationログ、Webhookキュー、日次突合、監視、Runbook | P0障害シナリオを自動テストで通過 |
| G3: 購入体験 | `/book`、チェックアウト、最終確認表示、会員／ゲスト方針、5言語、アクセシビリティ | UX・法務・計測の受入基準を通過 |
| G4: 限定本番 | 1物件・限定トラフィック・feature flag、監視付き実決済、ロールバック演習 | 連続運用で整合差異ゼロ、運営承認 |
| G5: 全面切替 | 広告切替、noindex解除、KPI監視、毎日突合 | 2週間のハイパーケア終了基準を満たす |

`BOOK_PREVIEW=1`、Basic認証、`noindex` は開発用の便利策ですが、機密性・決済安全性・本番相当性を保証しません。Stripe／Beds24／Firebaseは、原則としてtestとliveを分離し、検証用物件・検証用Webhook・検証用メール宛先を準備してください。また、ロールバックは表示だけでなく、処理中予約・PaymentIntent・広告URL・計測を含む手順として演習する必要があります。

## 最終所見

この案件は、見栄えのよい予約画面を作る案件ではなく、**「予約・決済・在庫・法定名簿・現場オペレーションを、障害時にも矛盾なくつなぐ基幹業務案件」**です。そこを軽く扱うと、最初の数件は動いても、予約競合、カード失敗、取消、問い合わせ、監査で必ずコストが跳ね返ります。

逆に、Beds24を基幹に残す方針、Firestoreミラー、日次突合、サーバー側再見積り、手数料後出し禁止、規約同意証跡という土台は有望です。P0を閉じ、限定本番で整合性を実証できれば、MS4の広告切替は自信を持って進められます。**今は速度よりも、分散トランザクションと責任分界を一度きちんと設計する局面です。**
