# 設計図: 予約明細の取り込み（Beds24 → `reservations`）

2026-09-01 起票／発注者の指示: **B案（実効の手取り率を実測してから使う）**を採用

## なぜ要るか

確定売上（`revenue`・手取り）は、運営会社との契約上の精算サイクルで
**前月分が翌月の下旬に届く＝1ヶ月遅れ**（`assumptions/revenue-lag`。
実測: 2026-07分の報告書の取込が 2026-08-27）。これは仕様であって台帳の不備ではない。

**遅れそのものは1ヶ月で、大きな問題ではない。** 本当の穴は別のところにある——
資金繰りが見るのは**これからの12ヶ月**で、そこには定義上ひとつも実績が無い。
いまは 2026-07 までの実績平均 ¥1,292,417 を**12ヶ月すべてに一律で置いている**。

2026-09〜2026-11 に ¥36,000,000・¥43,000,000 の支払いが並び、月末残高が ¥4,284,832 まで
落ちる局面で、**入金だけが過去の平均**という状態になっている。

### ただし予約は確定売上ではない（2026-09-01 発注者指摘）

宿泊業なので、予約をそのまま入金として積むのは誤り。3つの理由がある。

1. **キャンセル** — 入っている予約が消える
2. **直前予約の上積み（ピックアップ）** — 月初時点で見えている予約は、その月の最終実績より
   ずっと少ない。いま見えている9月の予約をそのまま積むと**過小に出る**
3. **料金の変動** — OTA側の値付けが動く

予約は「その時点までに積み上がっている量（on the books）」であって、確定額ではない。
したがって**予約で平均を置き換える**のではなく、**予約から幅を出す**設計にする。

## いま何があるか（調査結果・2026-09-01）

| 資産 | 状態 |
|---|---|
| `BEDS24_TOKEN`（読み取り） | Secret Manager に登録済み・稼働中 |
| `fetchBookings()`（`functions/src/beds24.ts`） | 実装済み。90日前〜550日先・全ページ・キャンセル込み・テスト物件を除外 |
| 物件ID / 部屋ID | `beds24Client.ts` に定義済み（清川 278158・高砂 291238） |
| `bookingDaily` | 稼働中（毎朝8:10）。ただし**泊数と稼働率だけで金額が無い** |

**追加のキー登録は不要。** 既存のトークンと関数で足りる。

## 保存するもの

`reservations/{bookingId}`。**一次事実だけ**を持ち、導出は保存しない（SSoT原則）。

| 項目 | 意味 |
|---|---|
| `bookingId` | Beds24 の予約ID（ドキュメントIDと同一） |
| `prop` | 棟（`kiyokawa` / `takasago`。FirestoreのIDと同一文字列） |
| `roomId` | 部屋 |
| `arrival` / `departure` | チェックイン / チェックアウト（`YYYY-MM-DD`） |
| `numNights` | 泊数（Beds24 の返り値。自分で引き算しない） |
| `numAdult` / `numChild` | 人数 |
| `status` | `confirmed` / `new` / `cancelled` など Beds24 の値をそのまま |
| `channel` | OTA名（`referer`） |
| `price` | 宿泊料の総額（Beds24 の値） |
| `commission` | OTA手数料（Beds24 が持つぶん） |
| `bookingTime` / `cancelTime` | 予約日時 / 取消日時 |
| `source` / `syncedAt` | 出典と取得時刻 |

**保存しないもの**: 稼働率・ADR・OTA別構成・月別の売上・手取り見込み。
すべて読むときに計算する。

## ピックアップとキャンセル率の出し方

予約1件ずつに `bookingTime` と `cancelTime` があるので、
**過去のある日時点で、ある月に何泊入っていたか**を後から再現できる。これを使って実測する。

1. 過去の各月 M について、「M の n 日前の時点で入っていた金額」と「M の最終実績」を並べる
2. 残り日数ごとの**上積み率**（最終 ÷ その時点）を出す。例: 30日前の時点なら最終はその1.6倍、
   といった曲線が棟ごとに得られる
3. **キャンセル率** = 一度入った予約のうち、最終的に `cancelled` になった金額の割合。
   これも残り日数ごとに出す（直前ほどキャンセルは減る）
4. 結果を `assumptions/pickup-curve` に棟別で保存する（人が見て納得して使う数字）

**そのため取り込みの範囲は 90日前ではなく、清川の開業（2025-06）まで遡る。**
曲線を学習するには、完了した月が十分に要る。

実測できるまでは**上積みを 0 とする**（＝下限のみを出し、見込みは出さない）。
分からないものを埋めて見せない。

## 手取り率の決め方（B案）

Beds24 が返すのは**宿泊料の総額**、法人の口座に入るのは**運営会社を通した手取り**。
あいだに OTA手数料と運営委託料（`assumptions/management-fee`・棟数連動 17%→13%）が入る。

係数で割り戻さず、**実測する**:

1. `revenue`（手取りの月次実績。清川14ヶ月・高砂11ヶ月）と、同じ月に
   チェックアウトした予約の `price` 合計を突き合わせる
2. 月ごとの `payout ÷ price合計` を出し、**直近6ヶ月の中央値**を実効手取り率とする
   （平均でなく中央値。1件の長期滞在や返金で寄るのを避ける）
3. 結果を `assumptions/payout-rate` に**棟別**で保存する（人が見て納得したうえで使う数字なので、
   導出だが例外的に保存する。`basis` に「どの月を使ったか」を残す）
4. 実測できない棟（六本松・大手門）は、**高砂の率を当てる**——いまの稼働見込みと同じ考え方

突き合わせの基準は**チェックアウト月**とする（精算がその月に立つため）。
ずれが大きい月があれば、その月を除外せず**そのまま見せる**（除外の判断を機械にさせない）。

## 取り込みの動き

新しい定期関数 `agencyBookings`（毎朝・既存の `fetchBookings()` を再利用）:

1. Beds24 から 2025-06（清川の開業）〜550日先を取得。
   初回は範囲が広いので分割して取る
2. `reservations/{bookingId}` に `merge: true` で冪等に upsert
3. **キャンセルは消さず `status: cancelled` のまま残す**（消すと「無かったこと」になり監査できない）
4. 取得0件・API エラーのときは**何も書かずに throw**（fail-closed。古い数字を新しい顔で見せない）
5. 初回実行がそのままバックフィルになる

Beds24 側に無い予約（手動削除など）はこちらにも残るが、`syncedAt` が古いままなので
「最後に見えていた日」が分かる。

## 画面への反映

### 資金繰り（`cashflow`）
毎月の入金を、月ごとに次の順で決める:

1. `revenue` に確定の手取りがある月 → **それを使う**（一次事実が最優先）
2. 無い月で、予約がある月 → **下限と見込みの2つ**を出す
   - **下限** = いま入っている予約 × (1 − キャンセル率) × 実効手取り率
     ——これ以上は減らない、という線
   - **見込み** = 下限 ＋ ピックアップの上積み（下記）
3. どちらも無い先の月 → いままでどおり実績の平均

**資金繰りの残高は「下限」で引く。** 手元が薄い局面の判断に使う数字なので、
入金は控えめに見る。見込みは表に併記するだけにする。

表には「この月の入金が**実績／予約／平均**のどれか」を必ず示す。混ぜたまま同じ顔で出さない。

### 定期レポート（`reports`）
稼働率・ADR・OTA別構成を出せるようになる（読むときに計算）。

### 六本松・大手門の稼働見込み
いまの「高砂の同じ暦月の手取り実績をそのまま当てる」は残す。
予約データが貯まれば、部屋タイプと単価から積み直す案に差し替えられる——ただし**今回の範囲外**。

## やらないこと

- Beds24 への書き込み（読み取りだけ。`BEDS24_WRITE_REFRESH` は触らない）
- ゲストの氏名・連絡先の保存（**個人情報は持たない**。資金繰りに要らない）
- `bookingDaily`（定点）の変更（別の目的で動いているものに手を入れない）
- 稼働率やADRの保存（読むときに計算する）

## 検査（`health` に足す）

| 検査 | 不合格の条件 |
|---|---|
| 予約の鮮度 | 最終取得が2日以上前 |
| ピックアップの学習 | 曲線を出せる完了月が6未満（＝下限しか出せない状態が続いている） |
| 手取り率の妥当性 | 実効手取り率が 50% 未満 または 95% 超（突合のずれを疑う） |
| 突合できた月数 | 直近6ヶ月のうち突合できた月が3未満 |

## 段取り

1. この設計図の承認
2. `agencyBookings` の実装＋テスト（純関数: 突合と中央値の算出）
3. 手動で1回実行 → 実効手取り率とピックアップ曲線を発注者に提示して**承認をもらう**
4. 承認後に資金繰りへ反映
5. `health` の検査を足す

**3で人の承認を挟む。** 実測した率をそのまま資金繰りに流し込まない——
数字が実感と合わないときに、機械が勝手に決めた状態にしないため。
