# 仕様書: 空室アラート（満室で断った人をリードに変える）

**作成**: 2026-09-03
**状態**: 実装済み・未デプロイ（2026-09-03）。プライバシーポリシーの追記は本番反映済み
**規模**: 3〜4日
**対象**: 予約ページ／新規Function／既存の定期実行／プライバシーポリシー（5言語）

---

## 1. 背景 — 月188人が行き止まりになっている

実測（2026-08-04〜09-02・30日）:

```
満室を見た            436回 / 188人
  代替日を提示        284回  →  選択  9回   採用率 3.2%
  他の棟を提示         71回  →  選択  4回   採用率 5.6%
```

**代替日の提案はほぼ機能していない。** 提示284回に対し9回。

一方、在庫は構造的に足りない（10月は2棟あわせて3連泊できる開始日が1通り）。**満室そのものは当面解消しない**ため、「断るしかない需要をどう扱うか」が問題になる。

登録率10%でも**月19件**。希望日つきで残るので、キャンセルが出たときに直接送れる。実際、直販でも自己キャンセルは発生しており、OTA側のキャンセルも `beds24CancelWatcher` で毎日検知している。

---

## 2. 何を作るか（v1のスコープ）

**満室画面でメールアドレスを受け取り、その日程が空いたら1回だけ知らせる。** それだけ。

やらないことは §7 に明記する。

### 2-1. 画面（`book/index.astro` の満室ブロック）

現在の満室表示（`bk-quote-out`）と代替日提案はそのまま残し、その下に置く。

```
この日程は満室です
（既存の代替日提案）
──────────────────────────
空きが出たらお知らせします
[ your@email.com          ] [ 通知を受け取る ]
2026年10月2日〜10月4日・4名の空室が出た場合に、1回だけメールでお知らせします。
配信はこの1通のみで、他の案内は送りません。
```

- 送信で GA4 `alert_signup`（`prop` / `nights` / `guests` / `lang`）
- Meta は `Lead` を送る（直販の見込み客。OTA流出の `OutboundBookingClick` とは別）

### 2-2. 保存（Firestore `availability_alerts`）

```
email        string    小文字化・trim
prop         string    kiyokawa | takasago | any（どちらでもよい場合）
checkin      string    YYYY-MM-DD
checkout     string    YYYY-MM-DD
guests       number
lang         string
status       string    pending | notified | expired
createdAt    timestamp
notifiedAt   timestamp | null
unsubToken   string    配信停止・取消用（ランダム）
```

**氏名・電話は取らない。** メールアドレスのみ。

### 2-3. 受け口（新Function `alertSignup`）

既存の `contact`（`functions/src/index.ts` L109〜）と同型で作る。

- CORS は `corsOrigin()` を再利用
- `rateLimited("alert:" + clientIp(req), 5, 600000)`（10分5回）
- メール形式の検証、`checkin < checkout`、`checkin` が未来、`guests` が定員以内
- 同一メール×同一日程の重複は上書き（増殖させない）

### 2-4. 照合と送信（既存の定期実行に相乗り）

`beds24CancelWatcher`（毎日 09:00 JST・`functions/src/index.ts` L941）の**直後に処理を足す**。新しいスケジュールは作らない。

```
pending のアラートを取得
  → checkin が過ぎていれば status=expired（送らない）
  → bookingRules + Beds24 在庫で、その日程・人数が予約可能か判定
      prop=any の場合は2棟のどちらかが空いていればよい
  → 可能なら メール送信 → status=notified・notifiedAt を記録
```

**1件につき1通で終了。** 空いた→また埋まった→また空いた、で繰り返し送らない。

想定件数は月19件程度なので、逐次処理で足りる。

### 2-5. メール（5言語・`mail-template.ts` の `mailHtml` を使う）

- 件名: 「【yah.homes】ご希望の日程に空きが出ました」
- 本文: 棟名・日程・人数・**予約ページへの直リンク**（`/xx/book/?prop=…&checkin=…&checkout=…&guests=…`）
- **「先着順で、他のお客様が先に予約される場合があります」を明記**（空室を確保するものではない）
- **配信停止リンク**（`unsubToken`）を必ず入れる — 特定電子メール法
- 送信者情報（ボンファイア株式会社・所在地・連絡先）はフッタの既存部品を使う

## 3. プライバシーポリシーの追記（着手前に必要）

> **【2026-09-03 完了】** 本番反映済み。ただし当初「5言語ぶん追記」としていたのは誤りで、
> 本文は全言語で日本語のまま提供している（各言語ページに法定公表である旨の注記が付く）ため、
> **追記は日本語1項目**とした。あわせて `firestore.rules` は初期値が全 deny のため、
> `availability_alerts` はクライアントから読み書きできない（Admin SDK のみ）。ルール変更は不要。

**メールアドレスは個人情報**であり、現行のポリシーは Google Analytics と Meta ピクセルしか書いていない。**5言語すべてに追記が必要。**

記載すべき内容:

- 取得する情報: メールアドレス、希望する宿泊日程・人数
- 利用目的: 希望日程に空室が出た場合の通知（1回限り）
- 第三者提供: しない
- 保存期間: 通知後または宿泊日経過後に削除
- 配信停止・削除の方法: メール内のリンク、または問い合わせ窓口

**この追記が完了するまで、機能を公開しない。**

## 4. 検証

| # | 確認 | 期待 |
|---|---|---|
| 1 | 満室の日程で登録 | Firestore に `pending` で1件。GA4 `alert_signup` が届く |
| 2 | 同じメール・同じ日程で再登録 | 増えず上書きされる |
| 3 | 10分に6回送信 | 6回目が 429 |
| 4 | 対象日程の予約をキャンセル → 翌9:00 | メールが1通届く。`status=notified` |
| 5 | もう一度空きが出る | **2通目は届かない** |
| 6 | `checkin` を過ぎたアラート | `status=expired`・送信されない |
| 7 | 配信停止リンク | 該当ドキュメントが削除される |
| 8 | メール内の予約リンク | 日程・人数が入った状態で予約ページが開く |

**判定（1ヶ月後）**: 登録数。月10件を超えれば継続。1桁なら文言か置き場所を見直す。

## 5. 見込み

```
満室で行き止まり  月188人
  × 登録率 10%   →  月19件のリード
  × 通知後の予約率（不明）
```

**通知後の予約率は未知数**であり、この仕様では約束できない。ただし:

- 希望日が明示された見込み客リストは、他に代えがたい
- Meta のカスタムオーディエンスに使える（リターゲティングの母集団）
- 「いつが埋まりやすいか」の需要データが貯まる（棟を増やす判断材料）

**リード獲得それ自体を成果とみなし、予約への転換は次の段階で設計する。**

## 6. リスク

| リスク | 対策 |
|---|---|
| スパム投稿でFirestoreが汚れる | rateLimited＋メール形式検証＋同一日程の上書き |
| 通知したのに既に埋まっている | 文言で「先着順」を明記。空室確保はしない |
| 迷惑メール扱い | 1件1通のみ。配信停止リンク必須。既存SMTP（contact@mail.yah.homes）を使う |
| 個人情報の取り扱い | §3 の追記完了まで公開しない。氏名・電話は取得しない |
| `beds24CancelWatcher` を壊す | 既存処理の**後ろ**に追加し、try/catch で囲んで既存処理に影響させない |

## 7. v1でやらないこと

- **即時通知**（キャンセル発生と同時）— OTA側のキャンセルは Beds24 のポーリングでしか分からない。日次で開始する
- **複数日程の登録**・**柔軟な日程**（「10月のどこか」）— まず固定日程で需要を見る
- **管理画面** — 件数は日次メールに1行足すだけ。専用画面は件数が増えてから
- **予約の仮押さえ** — 先着順のまま
- **SMS / LINE** — メールのみ
