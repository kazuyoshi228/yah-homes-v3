## 1. 背景 — ログイン画面は「押されてすらいない」

実測（2026-08-04〜09-02・30日・人数）:

```
決済画面に到達        14人
  ↓ 21%
ログインを操作した      3人   ← うち1人は一度失敗（auth_failed）
  ↓
予約データ作成         2人
決済フォーム表示       2人
決済承認              2人
```

**14人中11人（79%）が、ログインを一度も試さずに離れている。** 直近2週間でも 11人中8人（73%）で傾向は同じ。

`auth_completed` は5人だが、これは**セッション復元による自動ログインを含む**ため通過率の分母には使えない（`auth_started` 3人より多いのはそのため）。

### 原因

決済ページを開いた時点で、**ログイン以外のすべてが `hidden`**（`checkout.astro` L307/347/366）。認証が通って初めて表示される（L571-572）。

```
現在:  [ログイン] → お客様情報 → 宿泊規則 → お支払い
```

左の予約サマリ（棟・日程・料金）は見えるが、**何を入力させられるのか・規則は何か・支払いはどう進むのかを一切見せないまま、アカウント作成を求めている。** 3ステップ表示（日程・棟／お客様情報／お支払い）にも認証は存在せず、UIの説明と実装が食い違っている。

## 2. 変更後の流れ

```
変更後:  お客様情報 → 宿泊規則 → [同意して支払いへ] → ログイン → お支払い
```

1. **ページ読み込み時**: `co-details`（お客様情報）と `co-rules`（宿泊規則）を最初から表示。`co-auth` は隠す。`co-pay` のボタンは表示し、決済フォーム（`co-payment-element`）は従来どおり隠す
2. **`co-pay-btn` 押下時**
   - 未認証なら → `co-auth` を表示してそこへスクロール。`auth_prompted` を送る。**ここでは予約作成しない**
   - 認証済みなら → 従来どおり `bookCreate` → PaymentIntent → 決済フォーム表示
3. **認証完了時**（`onAuthStateChanged`）→ `co-auth` を隠し、**押下時の操作を再開**して `bookCreate` へ進む

ボタン活性条件（`sync`：規則同意＋氏名＋電話）は**変更しない**。

### ステップ表示の整合

`setStep(2)` は認証完了時ではなく**ページ読み込み時**に呼ぶ（お客様情報の入力中＝ステップ2）。決済フォーム表示時に `setStep(3)`。

## 3. 見落とすと事故になる点 ★重要

### 3-1. メールリンク認証で入力内容が消える

認証方式は2つある。

| 方式 | 挙動 | 現状 | 変更後 |
|---|---|---|---|
| Google | `signInWithPopup` — ページを離れない | 問題なし | 問題なし |
| **メールリンク** | `sendSignInLinkToEmail(auth, addr, { url: location.href })` でメールのリンクから**ページを開き直す** | 認証が先なので**入力前**。失われるものがない | **入力後に開き直すため、氏名・電話・代表者・到着時刻・同意チェックがすべて消える** |

コード内のコメント「戻り先URLに予約条件を保持するため状態は失われない」は、**URLパラメータ（prop / checkin / checkout / guests）についての記述**であり、フォームの入力値は含まれない。

**対策**: メールリンク送信の直前にフォーム値を `sessionStorage` へ保存し、ページ読み込み時に復元する。

```js
const FORM_KEY = `yah_checkout_form:${prop}_${checkin}_${checkout}_${guests}`;
const FORM_FIELDS = ["cf-name", "cf-phone", "cf-cc", "cf-lead", "cf-arrival"];
// 保存（co-email-send 押下時）／復元（読み込み時）
```

**同意チェック（`cf-rules`）は復元しない。** 規則への同意は本人の明示的な操作として毎回取る。

### 3-2. Google認証が氏名を上書きしない

現在 `onAuthStateChanged` は無条件で `$("cf-name").value = user.displayName || ""` を実行する。変更後は**利用者が先に入力している**ため、**空のときだけ**入れる。

```js
if (!$("cf-name").value.trim()) $("cf-name").value = user.displayName || "";
$("cf-email").value = user.email || "";   // email は readonly なので常に上書きしてよい
```

### 3-3. メールアドレス欄（`cf-email` は `readonly`）

認証で埋まる項目のため、認証前は空になる。**認証前は行ごと隠す**。認証後に表示して埋める。空の必須readonly欄を見せない。

### 3-4. 認証後の自動再開

利用者は既に「同意して支払いへ」を押している。認証完了後に**もう一度押させない**（意図の取り直しは不要で、離脱を増やす）。ただし再開するのは**予約作成と決済フォーム表示まで**で、**課金は従来どおり2回目の押下**。ここは変えない。

## 4. 計測の追加

現状は「決済画面に来た」の次が「ログインを操作した」しかなく、**フォームを埋めたのに離脱した人**が見えない。

| イベント | 発火 | パラメータ |
|---|---|---|
| `checkout_form_started` | いずれかの入力欄に最初に触れたとき（1回だけ） | `prop`, `seconds` |
| `auth_prompted` | 「同意して支払いへ」押下で認証を出したとき | `prop`, `seconds` |

これで判定できるようになる:

```
checkout_viewed → checkout_form_started → auth_prompted → auth_started → auth_completed → payment_form_shown
```

**キーイベントにはしない**（Google Ads に取り込ませない。直販の成果は `purchase` で測る）。

## 5. 検証

| # | 確認 | 期待 |
|---|---|---|
| 1 | 未ログインで決済ページを開く | お客様情報と宿泊規則が**最初から見える**。ログイン欄は出ていない |
| 2 | 氏名・電話・同意を入れて押下 | ログイン欄が現れ、そこへスクロール。`auth_prompted` が届く |
| 3 | Googleでログイン | 入力値が保持されたまま、決済フォームまで自動で進む |
| 4 | 氏名を入れてからGoogleログイン | **入力した氏名が上書きされない** |
| 5 | **メールリンクで認証**（別タブで開き直す） | 氏名・電話・代表者・到着時刻が**復元される**。同意チェックは外れている |
| 6 | ログイン済みの状態で開く | ログイン欄を経ずに、従来どおり決済まで進める |
| 7 | 決済フォーム表示 → 2回目の押下 | 従来どおり課金される（**ここは変えていない**） |
| 8 | 定員超過・受付終了などのエラー | 従来どおり表示される |

**判定（1ヶ月後）**: `checkout_viewed → auth_started` が 21% から上がるか。母数は月14人なので、**40%を超えるような明確な変化しか読み取れない**ことは承知の上で見る。あわせて `checkout_form_started` の比率で「フォームに触れたか」も分かるようになる。

## 6. リスクと巻き戻し

| リスク | 対策 |
|---|---|
| **メールリンク認証で入力が消える** | §3-1。検証⑤で必ず確認する |
| 認証後の自動再開が二重に走る | 再開は1回のみのフラグで制御する |
| Google認証が氏名を上書き | §3-2。検証④で確認 |
| 未認証で `bookCreate` を呼んでしまう | `currentUser` が無ければ認証を出して**必ず return** する |
| 既存のログイン済み利用者の体験が壊れる | 検証⑥ |

**サーバー側は一切変更しない。** `bookCreate` は従来どおり ID トークンを要求し、未認証の予約は作れない。**変えるのは表示順だけ**であり、認証の必須性は維持される。

**巻き戻し**: 1ファイルの変更。`git revert` → 再ビルド → デプロイで戻る。

## 7. やらないこと

- **ゲスト予約**（アカウント不要で予約完了）— 変更・キャンセル導線の再設計が必要で規模が大きい。**本件の結果を見てから判断する**
- **認証方式の追加**（LINE・Apple 等）
- **課金タイミングの変更** — 2回目の押下で確定、は維持する
