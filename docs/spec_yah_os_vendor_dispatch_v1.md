# yah.OS 業者ディスパッチ仕様書 v1.2 — メールベース（2026-08-19 更新・モック確定状態を反映）

外部委託（清掃・リネン等）・点検（法定・定期）・**内部の定期作業（chatの棚卸し等）**の
「起票 → 通知/手配 → 作業 → 検品 → 完了」をAIに委任する仕組み。自動化100%提案書 Phase 6 の詳細仕様。
ジョブの宛先が業者か内部かが違うだけで、周期エンジンは全作業共通の1つ。
**カード対応（2026-08-19 発注者決定）**: 外部業者が動くジョブ＝「外部委託」カード（清掃・点検・修繕）、
内部（AI・自分たち）が動く周期ジョブ＝「定期メンテナンス」カード。点検は独立カードにしない。
**v1はメールのみ**。LINEはチャネル口だけ設計しておき、実装はv2（§9）。

## 0. 前提と適用範囲（重要）

- 現行の清掃・現地対応は**Airstarの手配範囲**。本仕様のv1適用先は、
  **自社が直接契約する委託**（消防・浄化槽・エアコン等の点検業者、スポット修繕）から始める。
  清掃への適用は、Airstarとの役割分担の合意後（勝手に二重手配しない）。
- 業者側に要求するものはゼロ: いつものメールで返信するだけ。アプリ・画面・登録なし。

## 1. プロセスと委任範囲

| 工程 | 内容 | 担当 |
|---|---|---|
| ① ジョブ生成 | 予約・暦から作業ジョブを自動起票 | 機械（完全自動） |
| ② 依頼送信 | 標準の作業依頼メールを業者へ送付 | 機械 |
| ③ 日程アレンジ | 業者返信を読解し、制約内で代替日を提案・合意 | **AI**（v1の核） |
| ④ 完了確認 | 完了報告（写真添付）の受領・検証・催促 | 機械＋AI |
| ⑤ 例外 | 破損・ドタキャン・品質問題・判断に迷う返信 | **人間へ即エスカレーション** |
| ⑥ 契約・単価 | 業者選定・値上げ・契約更改 | 人間（対象外） |

## 2. データ設計（Firestore **名前付きDB `os`**・2026-08-19 発注者決定）

運営コンソール系のデータは既定DBに置かず、**専用DB `os` を新設**する（chat が `chat` DB で
分離しているのと同じ型）。既定DBは公開読み取り前提のコレクション（property_facts 等）を含む
ゲスト向けドメインであり、業者・ジョブ・周期などの内部運営データとは守秘水準もルールも違うため。
- ルール: `os` DB はクライアント直アクセス全面拒否（読み書きは Functions 経由のみ）
- 予約の参照: ジョブ生成は既定DBの bookings を**読むだけ**（Admin SDK は複数DBを同時に扱える）
- 呼称（2026-08-19 発注者と整理）: 既定DB=**Web SSoT**（サイトが公開する事実）/ `chat` DB=**chat SSoT** /
  `os` DB=**OS SSoT**（運営の事実）。正本は「その事実に責任を持つドメイン」にだけ置き、
  **ドメイン越境は読み取りのみ**（書きが2ドメインから入る事実を作らない）


```
vendors/{vendorId}        業者マスタ
  name / email / channel("email"・将来"line") / 対応施設[] / 作業種別[]
  稼働不可曜日・時間帯 / 窓口担当者名 / 備考
jobs/{jobId}              作業ジョブ（起票〜完了まで一生を記録）
  prop / type("清掃"|"点検"|"修繕") / trigger(予約ID or 周期キー)
  window { from, to }     作業可能窓
  status: draft → sent → negotiating → confirmed → done → verified
          （どこからでも exception へ遷移可）
  vendorId / 合意日時 / 完了報告 { at, photos[], note }
jobs/{jobId}/messages/{n} 送受信ログ（方向・本文・添付・AI解釈・確信度）
schedules/{key}           周期マスタ（施設×種別×周期×基準日×担当業者×**予算/回**）
                          ※予算は計画値。実績はMF仕訳が正本で、会計処理カードが両者を突合して超過アラート
```

### 2b. 履歴の設計（2026-08-19 発注者確認: 履歴は本体）

- **append-only**: ジョブは削除・上書きしない。状態遷移のたびに日時・AI判定（確信度つき）を追記し、
  `jobs` に永久蓄積。カレンダーの過去年はこの蓄積の描画（未来=schedules・過去=jobs）
- 3層: ジョブ本体（os DB）/ やり取り（jobs/{id}/messages ＋ Gmail原本=二重証跡）/
  証拠物（完了写真・報告書PDF → Cloud Storage **専用バケット `yah-homes-os-archive`**・非公開・
  既定バケットと分離。バックアップは `yah-homes-backups` へ週次エクスポート）
- 集計先: **業者の成績表**（返信時間・遅延率・品質 → 契約更改の材料をAIが自動作成）/
  **施設のメンテナンス履歴**（売却・金融商品化のDD開示資料。履歴付き資産は高く売れる）/
  AI改善材料（例外・誤読・人間の上書きの記録 → 月次恐竜化チェックで読解を改善）
- 法定書類の保管年限は永久保存方針で自動的に充足。Firestore 定期エクスポート（GCS）を
  バックアップとして自動化に含める（履歴が本体である以上、履歴の保全も fail-closed の一部）

- **鍵・キーボックス暗証番号は指示書・メールに載せない**（既存鉄則。入室情報は現行の別経路のまま）。
- 単価・支払情報はジョブに持たない（⑥は対象外のため。経費はMF側で締まる）。
- **設備台帳（equipment/・2026-08-19 発注者指示でカード化）**: 施設×設備（給湯器・エアコン・
  洗濯機・スマートロック等）の型番・設置日・保証期限・保証書PDF（Storage）。
  修繕ジョブ起票時にAIが該当設備を特定し**保証期間内なら業者ではなくメーカー窓口へ振り分け**。
  電池交換など消耗サイクルは schedules と連動。新棟プロビジョニングで雛形をシード。

## 3. ジョブ生成（①）

- **清掃**: 毎朝、bookings から翌日以降のチェックアウトを走査して起票。
  作業窓 = 退室時刻〜次予約の入室時刻（次予約が無ければ余裕窓）。リネン数 = 宿泊人数。
  ※Airstar合意後に有効化するフラグ付きで実装（§0）。
- **点検・年次作業**: schedules の周期（例: 消防設備 年2回・浄化槽 年1回）から期日60日前に起票。
  作業窓は広く取り、予約とぶつからない日を優先提示。
- **自律サイクル（2026-08-18 発注者指示: 年1回の作業も登録後はAIが勝手に手配まで完結）**:
  ジョブが verified になった時点で、**次回分を自動で再登録**（完了日＋周期）。
  一度 schedules に載せた作業は、以後人間が思い出す必要がない。
  「去年やったか覚えていない」を構造的に消すのが目的。
- **年次作業カタログ（初期シード・施設ごと）**:
  - 業者手配型（本仕様のAIが手配まで実行）: 消防設備点検（年2回・法定）/ 浄化槽の保守・清掃 /
    エアコン洗浄 / 排水管高圧洗浄 / 防虫・防鼠 / 外壁・屋根・雨樋の目視点検 / 植栽剪定 /
    スマートロック等の電池交換（稼働日数起点）
  - 事務手続き型（業者ではなく手続き。AIは起票・書類準備・期日管理まで行い、
    実行は承認キューで人間が1クリック）: 火災保険の更新 / 旅館業関連の報告・更新物 / 各種契約更改
- **内部作業ジョブ（2026-08-19 発注者指示: 周期の通知→作業→検品までAIで完結）**:
  宛先が業者ではなく「内部」のジョブ。schedules に同じ形で載り、**作業の実行もAIが担う**。
  | 定期作業 | 周期 | AIの作業 | 検品 |
  |---|---|---|---|
  | チャット用情報の棚卸し | 年1回・新棟追加時 | 全設問の回答とSSoT・実態の差分案を生成 | 整合チェック機械検査→人が承認 |
  | RAGドキュメントの鮮度確認 | 半年 | 参照先の変更検知・古い記述の洗い出し | 同上 |
  | 恐竜化チェック（chat品質） | 月1 | 会話ログからレポート自動生成 | しきい値判定→悪化時のみ人へ |
  | モデル・プロンプト見直し | 四半期 | エスカレーション率推移＋新モデル情報の要約 | 人が判断 |
  | AirDNA月次チェック・進出スコア更新 | 月1 | チェックリストの下書きと前月差分 | 人が15分で確定 |
  | 保険・契約などの更新（事務型） | 契約ごと | 書類準備・期日管理 | 実行は人が1クリック |
  - **検品の原則**: 作業したAIが自分で合格判定しない。検品は別の機械検査（SSoT整合・
    禁止事項スキャン・しきい値）を通し、**SSoTの書き換え・公開を伴うものは必ず人の承認**で確定
    （鉄則1と同じ構造。人の作業は「読む・押す」だけに圧縮する）
  - 作業リンク: ジョブには実行画面（chat admin等）への直リンクを付ける。実体は各ドメインの
    管理画面・暦と催促はこのエンジン、という分業（実体とカレンダーの分離）
- **新棟プロビジョニングとの接続**: 新しい施設を立ち上げる際、法定・推奨サイクル一式を
  雛形から自動シードする（「物件立ち上げの型」の一部。棟が増えても年次管理の手間はゼロのまま）。
- **突発ジョブ（type: "spot"・2026-08-19 発注者承認）**: タブは増やさず**ジョブの種別**として扱う
  （起票後の一生＝調整→確定→作業→検品→履歴は定期と完全に同じ）。
  - 入口は3つ: ①画面の「＋ 突発ジョブ」ボタン（作業内容・施設・写真を付けて手動起票）
    ②お客様chatのエスカレーションから「修繕ジョブ化」 ③点検報告書の指摘事項からAIが自動起票
  - **是正ジョブの自動連鎖**: 検品AIが点検報告書から指摘（例: 消火器の期限切れ）を抽出したら、
    是正ジョブ（spot）を自動起票して元の点検ジョブにリンク。是正→再確認まで追跡し、
    法定対応の抜け漏れを構造的に防ぐ
  - 表示: カレンダーは発生月に⚡マーク付きチップ・履歴は種別列（定期/突発）が増えるだけ。
    「突発が多い施設」は設備の健康状態のシグナルとして集計に使う
- 二重起票防止: trigger をキーに冪等。予約のキャンセル・日程変更時はジョブを自動で追随
  （confirmed 後の変更は業者へ変更依頼を自動送信し、negotiating に戻す）。

## 4. メール送受信（②・受信口）

- **送信**: 既存の mailHtml 基盤（SMTP）。件名に `[yah-{jobId}]` を必ず含める。
- **受信**: 専用アドレス **`ai@bonfire.co.jp`**（2026-08-19 発注者決定・業者との契約主体=法人のため
  会社ドメイン。yah.homes はお客様向けブランドに温存）。Google Workspace の独立ユーザーとして新設し、
  **Gmail watch（Pub/Sub プッシュ）で新着を即時に Functions へ**（ポーリング不要・数秒で応答）。
  - **受信箱=AIの作業場**: 人はいつでもGmailにログインして全やり取りを閲覧・自分で返信できる。
    スレッドに人間の送信を検知したらAIは自動で手を引く（引き継ぎ検知）
  - **ドライラン=Gmail下書き**: 学習期間はAIが下書きを作るだけで、送信は人が受信箱から。
    専用承認UIを作る前に Gmail が承認画面になる。解禁後も キルスイッチで下書きモードへ即戻せる
  - 権限は自箱のみ（最小権限・漏洩時の影響がこの1箱に閉じる）。コストは Workspace 1席
- 紐付け: 件名の `[yah-{jobId}]` → 無ければ From と直近ジョブから推定 → 推定不能は例外へ。
- 添付（完了写真）は Storage に保存し jobs.完了報告 に紐付け。

## 5. AI読解と日程アレンジ（③・④）

受信メールを LLM で分類し、状態機械を進める:

| 分類 | 動作 |
|---|---|
| 承諾 | status→confirmed。確認メールを返す |
| 日程NG | 制約（作業窓・業者の稼働不可・次予約）内で**代替日を最大3案**提示 |
| 質問 | ジョブ情報・SSoT（施設の事実）から回答。答えられない質問は例外へ |
| 完了報告 | 写真枚数・撮影時刻を機械チェック → verified。不足は不足分だけ催促 |
| 金額・契約の話題 | **即・例外**（⑥は人間の領域。AIは交渉しない） |
| 解釈に自信がない | **即・例外**（誤読で「合意したことにする」が最悪の事故） |

- 期限管理: confirmed の期日前日に業者へリマインド。完了報告が期日翌朝までに無ければ催促
  → さらに24時間で例外。

## 6. fail-closed（この仕組みの生命線）

1. **清掃ジョブ: 次のチェックイン48時間前までに confirmed でなければ人へ即アラート。
   24時間前までに verified でなければ最上級アラート**（「たぶん掃除済み」で通すことを構造的に禁止）
2. 点検ジョブ: 法定期日30日前までに confirmed でなければアラート
2b. **内部作業ジョブの放置アラート（段階制）**: 期日7日前にリマインド → 期日超過で警告 →
   14日超過で最上級アラート（メール・毎日）。ジョブは放置しても消えない・自動でverifiedに
   しない（「やったことになっている」を構造的に禁止）
3. AIの自動送信は**キルスイッチ**（Firestoreフラグ）で即・下書きモードに戻せる
4. 全送受信・状態遷移・AI解釈を jobs/messages と audit_logs に記録

## 7. 管理画面「外部委託」（2026-08-19 モックで確定・3ペイン＋5タブ）

3ペイン: 左=**施設スイッチャー**（すべて/施設別。カレンダー・定期作業・履歴を絞り込み）/
中央=5タブ / 右=**ジョブ詳細パネル**。

- **タブ① カレンダー**（自動生成・読み取り専用）: 月×施設のマトリクス（施設選択時は1列）。
  セル状態はジョブから自動反映: グレー=予定 / 青=確定 / 緑=完了(verified) / 赤=遅延。
  **完了操作は人が押さない**（業者の報告写真をAIが検品して緑になる）。遅延はセル赤＋メールの二重通知。
  完了→次回自動再登録で将来年も自動で埋まる。ヘッダに「**＋ 突発ジョブ**」ボタン。
  突発（spot）は⚡付き破線チップで同カレンダーに表示
- **タブ② 定期作業**（schedules の編集面）: 1行=作業×施設（施設列は置かず、文脈は左スイッチャー）。
  列: 作業・周期・業者・**予算/回**（計画値。実績=MF、会計処理が突合して超過アラート）・次回（自動）。
  行クリック→右パネルに「次回/その先の自動展開/履歴」
- **タブ③ 業者台帳**（vendors の編集面）: 会社名・担当・電話・メール・連絡チャネル・担当作業（自動集計）。
  行クリック→右パネルに「チャネル/担当定期作業/直近ジョブ・メモ」。メールの無い業者は
  「電話のみ・人が仲介」表示（AI自動化の対象外を明示）
- **タブ④ 施設**（施設台帳）: 施設×（状態・定期作業数・次回予定・遅延件数）。
  準備中の施設は「立ち上げ時に雛形を自動シード」と表示。行クリック→右パネルに施設詳細
- **タブ⑤ 履歴**（append-only の証跡ビュー）: 完了日・作業・施設・業者・証跡（写真枚数/報告書）・
  AI検品結果（合格・確信度）の時系列一覧。行クリックで当時のジョブへ完全に遡れる。
  **Excelコピー/CSV書き出し**（施設・期間で絞ってDD開示資料にそのまま使う）

### 7-2. ジョブ詳細パネル（右ペイン・状態別）

- 共通: 状態バッジ / 概要（予定・業者・窓口=ai@bonfire.co.jp）/ **タイムライン**
  （起票→依頼→調整→確定→リマインド→完了報告→検品→次回登録。進行点は緑・遅延は赤点）/
  やり取りログ（AI・業者・人の別を明示）/ 操作（**Gmailでスレッドを開く↗・自分で対応する=AI一時停止・
  ジョブ取消**。遅延時は「電話で確認した→日程を手で入力」を追加）
- 完了時: 完了写真サムネイル＋**AI検品カード**（合否・確信度・検査内容: 枚数/撮影時刻/対象の写り・
  次回自動登録の記録）
- 遅延時: **AI判定カード**（超過日数・催促履歴・毎日アラート送信中・推奨アクション）
- 突発時: 発生元（chat報告/点検指摘/手動）と設備台帳の照会結果（保証判定）を表示


## 8. 立ち上げ手順（ドライラン必須）

1. 業者マスタ整備（まず点検業者2〜3社・発注者作業: 各社の窓口メールの確認）
2. **1ヶ月は下書きモード**: AIは返信案を作るだけ、送信ボタンは人間。読解の癖を記録
3. 分類の的中率≥95%・例外の取りこぼしゼロを確認して自動送信を解禁
4. 清掃への拡大は Airstar 合意後（§0）

## 9. LINEへの拡張（v2・口だけ先に切っておく）

- 送受信をチャネルアダプタとして抽象化: `send(job, message)` / 受信正規化 → AI以降は共通。
- v2で LINE公式アカウント（Messaging API・Webhook受信）を追加し、vendors.channel で
  業者ごとに出口を切替。現場系=LINE・フォーマル系=メールの使い分けを想定。
- 個人LINEの自動化は行わない（API非提供・規約違反のため）。
