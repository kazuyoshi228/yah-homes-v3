# 提案書: yah.OS を自動化100%へ持っていく道筋 v1（2026-08-18）

自動化仕様書（spec_yah_os_automation_v1.md）が「今ある手動をなくす」計画であるのに対し、
本書は「**100%とは何か・どう到達するか**」の設計思想と道筋を示す提案書。

---

## 1. 「自動化100%」の定義

「人間がゼロ」ではない。**定常運営における人間の作業時間をゼロ**にし、
人間に残るのは①週1回の承認キュー処理と②例外対応だけ、という状態を100%と定義する。

```
100% = 定常作業 0分/週 ＋ 承認キュー（週1回・15分以内）＋ 例外アラート対応
```

この定義を採る理由:
- 「判断も含めて全部AI」は鉄則1（AIに公開・送金の権限を持たせない）と矛盾し、事故時に守れない
- 一方「判断があるから自動化できない」は嘘。**判断のほとんどはルール化できる**。
  ルール化できない残りだけをキューに集めれば、判断は消えないが**作業は消える**

測る指標は1つ: **human-minutes/週/棟**（棟あたり週間人間作業分数）。
現在の推定 ≈ 90〜120分/週/棟 → 目標 0分（キュー処理15分/週は棟数に比例しない固定費）。

## 2. 自動化レベルの物差し

| レベル | 状態 | 例（現在） |
|---|---|---|
| L0 | 完全手動 | AirDNA調査・財務更新・PR |
| L1 | 道具はあるが人が実行 | GSC週次スクリプト・定点転記 |
| L2 | 自動実行・人が確認 | Beds24定点8:00・広告配信 |
| L3 | 自動実行・承認キューで1クリック | （目標形）記事公開・返金・価格改定 |
| L4 | 完全自動・例外のみ通知 | メール4通・chat・QR・OTAミラー |

**到達戦略はすべてのカードを L3 か L4 に上げること。**
L4にできるもの＝結果が可逆 or 金額が小さいもの。L3に留めるもの＝公開・金銭・価格。

## 3. 「自動化できない」とされる領域の攻略法

ここが本提案の核心。判断系5領域は、それぞれ**すでに合意済みの運用哲学がルールの形をしている**。

### 3-1. 価格改定 → L3〜L4
発注者の価格哲学がそのまま機械化できる:「値上げは実績トリガーの機械調整のみ・攻め値付けはしない」。
- ルール例: 「先付け稼働がしきい値超過→対象週を+n%」「直前空室→自動で微調整」。上限・下限・変更幅を固定
- 実装: 毎朝の定点に判定を同居→Beds24へ料金書き込み。当面はL3（提案をキューに出し1クリック承認）で
  3ヶ月運用→判定の的中を見てL4へ昇格

### 3-2. 広告予算（ツマミ）→ L3
種火方式は「全市場を最小予算で常時点火・増減はツマミだけ」。ツマミ操作こそルール化対象。
- ルール例: 「市場CPAが基準の1.5倍を2週連続→日予算を1段下げ」「0.7倍以下→1段上げ。ただし総額上限は固定」
- 上限変更（総額の引き上げ）だけは経営判断としてキュー外に残す

### 3-3. 返金 → ポリシー内L4・ポリシー外L3
無料期間内のセルフキャンセル返金は既にL4。残りは「ポリシー外の例外返金」だけ。
- ポリシー外は金額と理由をキューに載せ、Admin が1クリック（現行の返金画面を承認キュー化）

### 3-4. コンテンツ公開 → L3（鉄則1は不変）
AIが公開しない原則は守る。変えるのは人間側の作業量:
- 下書き生成→機械QA（整合チェック・SSoT照合・禁止事項スキャン）→**キューで差分プレビュー→1クリック公開**
- 人間の作業は「読む・押す」だけ。執筆・検証・投入の作業時間をゼロにする

### 3-5. 財務 → L3
- 月次クローズ（売上・チャネル・広告費・ユニットエコノミクス）は機械が締める
- 42ヶ月モデルの前提変更は「機械が乖離を検出→修正案をキューに提示→人間が採否」。
  保守基準の規律は、機械案に対しても保守側に丸める実装で担保

### 3-6. 物理領域（建築・清掃・現地対応）→ 指揮の自動化
ロボットは買わない。OSがやるのは**指揮**:
- 清掃・点検の依頼発行と完了確認（写真提出→機械チェック）を予約データから自動生成
- 運営会社（Airstar）との定型連絡をすべてシステム発行にし、電話・都度連絡を例外だけに
- 建築・立ち上げは「物件立ち上げの型」をコード化: **新棟プロビジョニング1コマンド**
  （property_facts雛形・chat施設・QR・how-to雛形・Beds24紐付け・名簿フォームを一括生成）。
  清川→高砂の横展開で手作業だった部分を全部潰す

## 4. 中枢のしくみ: 承認キュー（The Queue）

100%の要は、散らばった判断を**1つの受信箱**に集めること。

- 場所: /admin に「承認キュー」を新設。項目=（種類・根拠データ・機械の提案・実行ボタン・却下ボタン）
- 種類: 価格改定案 / 広告ツマミ案 / ポリシー外返金 / 記事公開 / 財務前提の修正案
- SLA: 週1回まとめて処理（緊急のみ即時通知）。**処理しなくても事故らない**設計
  （承認されるまで現状維持＝fail-closed。期限切れで自動実行するものは作らない）
- すべての承認・却下は audit_logs へ。却下理由は機械の学習材料（ルールの調整に使う）

## 5. ガードレール（100%を事故らせないための設計）

1. **変更幅の上限**: 価格±n%/週・広告予算±1段/週など、機械が一度に動かせる幅を固定
2. **キルスイッチ**: 自動化ごとに ON/OFF フラグ（Firestore）。1タップで手動運転に戻せる
3. **ドライラン期間**: 全てのL3/L4は最初の1ヶ月「実行せず提案だけ」で走らせ、的中率を見てから実行を解禁
4. **監査ログ**: 機械の全アクションを audit_logs に記録（すでに管理画面はこの型）
5. **恐竜化チェック**: 月1で「このルールはまだ正しいか」を機械自身がデータ付きで問い直すレポートを出す

## 6. ロードマップ（自動化仕様書の Phase 1–3 の先）

| 段階 | 内容 | 到達点 |
|---|---|---|
| Phase 1–3 | 仕様書のとおり（週次レポート→月次財務→常時監視） | 全カード L2 以上 |
| **Phase 4** | 承認キュー基盤＋公開キュー・例外返金キュー | 判断が1箇所に集まる |
| **Phase 5** | 価格・広告のルールエンジン（ドライラン→実行解禁） | 収益判断が L3 |
| **Phase 6** | 新棟プロビジョニング1コマンド＋清掃指揮の自動発行 | 立ち上げ・物理指揮が仕組み化 |
| **Phase 7** | ルール調整の半自動化（却下理由からのチューニング提案） | OSが自分を改善し始める |

各Phaseは独立して価値が出る（前のPhaseだけで止めても損しない）。着工は都度承認制。

## 7. これがPEストーリーに与える意味

- human-minutes/週/棟 という**1つの数字**で「運営が仕組みに載っている」ことを証明できる
  （財務カードの隣に置ける、恣意性のない指標）
- 承認キューの処理履歴は「経営者が週15分で何棟でも運営できる」ことの実記録になる
- キーマンリスクの反証: 判断がルールとキューに外在化されているため、人が替わっても回る

## 8. 決定が必要な事項

1. この「100%の定義」（定常0分＋週1キュー15分）で良いか
2. 価格改定の機械化に踏み込むか（価格哲学のルール化。ドライランから開始）
3. 承認キューを /admin に新設する方針で良いか
4. 着手順: まず自動化仕様書の Phase 1（週次レポート）から。本提案の Phase 4 以降は
   Phase 1–3 の完了後に個別仕様書→承認→実装
