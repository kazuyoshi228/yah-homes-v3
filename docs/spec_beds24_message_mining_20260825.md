# 仕様書 — Beds24 メッセージの定期回収と、チャットへの還元

- 状態: **提案・未実装（承認待ち）**
- 起票: 2026-08-25・定期レポート担当スレッド
- きっかけ: 「Beds24のメッセージボックスを定期的に回収して分析＞チャットに活かす、を自動化できない？」（発注者）

---

## 1. できます。ただし現状は「片道」

いまの実装:

| 向き | 状態 |
|---|---|
| 自社チャット → Beds24 | **○ 稼働中**（`postBeds24Note` で会話を複製・新規予約/キャンセル通知も） |
| **Beds24 → 自社** | **✕ 無い**。OTA（Airbnb/Booking）でゲストが送った文面は取り込まれていない |

つまり**OTAゲストの生の声が、いまはどこにも残っていない**。
Airbnb/Booking経由が予約の大半なので、**問い合わせの母数の大半が見えていない**状態。

## 2. 何のために回収するか（3つ・優先順）

### A. FAQ・定型文の材料 ★本命
「同じ質問が何回来たか」が分かれば、**チャットの定型文とサイトのFAQに反映**できる。
いまの限定自動応答（auto-limited）は文面が固定で、実際に多い質問から作られていない。

### B. エスカレーション話題の発見
既存の自動応答は「エスカレーション話題を含まないときだけ送る」判定を持つが、
**そのキーワード一覧が実データから作られていない**。回収すれば根拠のある一覧になる。

### C. 返信速度の実測
Booking のレビュー内訳で **ホスト評価8.1が相対弱**（baseline §1）。原因はレス速度と推定されている。
受信〜返信の時間差を測れば、**推定が事実になる**。

## 3. 設計

```
Beds24 API /bookings/messages（GET）
   ↓ 毎朝8:20  beds24MessageSync（appspot SA・既存トークンを流用）
Firestore agency/guestMessages/{beds24Id}_{seq}   ← 分析用の鏡
   ↓ agencyApi guestMessages（読むだけ）
定期レポート > 定点観測 > ゲストの声
```

- **正本はBeds24**。ここは分析用の鏡（消えても再取得できる）
- 毎朝、直近30日の予約に紐づくメッセージを取り直す（新着・編集を拾う）
- 初回は取得可能な範囲をバックフィル

### スキーマ

```
guestMessages/{id}: {
  bookingId, seq, at, source: "guest"|"host"|"internalNote",
  prop, channel: "airbnb"|"booking"|"direct",
  text,                       // 原文（分析に要る）
  lang,                       // 判定した言語
  topics: ["チェックイン", "駐車場", …],   // 分類（下記）
  syncedAt,
}
```

### 分類のしかた — まずキーワード、AIは後

**第1段はキーワード辞書**（チェックイン/鍵/駐車場/Wi-Fi/late/早着/ゴミ/設備の不具合/周辺/支払い…）。
理由: 件数がまだ小さく、AI分類はコストと不確実性に見合わない。辞書なら**なぜそう分類されたかが説明できる**。

第2段（件数が増えたら）: 未分類が一定数を超えたときだけAIに要約させ、**辞書に足す候補**として人へ出す。
AIに分類そのものを任せない——同じ文が日によって別の箱に入ると、推移が読めなくなる。

## 4. 個人情報の扱い（ここが一番大事）

ゲストのメッセージは**個人情報を含む**。運営委託契約 第7条（守秘義務）・個人情報保護法の対象。

| 決めごと | 理由 |
|---|---|
| **氏名・電話・メール・パスポート番号は保存前にマスクする** | 分析に要らない。持たなければ漏れない |
| 保存先は `agency` DB（owner限定API配下） | 既存の権限境界をそのまま使う。運営会社（Airstar）からは見えない |
| **画面に出すのは集計と本文の抜粋のみ**。ダウンロード機能は作らない | 持ち出しの経路を作らない |
| 保持期間 **13ヶ月**で自動削除 | 名簿の法定保管（3年）とは別物。分析に要るのは季節1周ぶん |
| 原本アーカイブに入れない | 再取得できる／個人情報を保管庫に増やさない |

**AIに本文を渡すのは第2段の未分類だけ**（§3）。その時も氏名等はマスク済みの本文のみ。

---

## 5. 画面（定点観測 > ゲストの声）

| 話題 | 件数（30日） | 前期比 | 代表的な文（抜粋） |
|---|---:|---|---|

- 日/週/月タブは付けない（件数が小さく、月次で十分）
- 右パネル: **定型文への反映候補**（件数が多いのに定型文が無い話題）＋ 返信速度の中央値
- 「未分類」の件数を必ず出す——辞書の穴が見えるように

## 6. チャットへの還元（自動化しない部分）

**回収と分析は自動、反映は人**にする。

- 定型文（`mail_templates`）の書き換えをAIが自動で行うと、**ゲストに届く文面が誰の承認も無く変わる**
- 画面が「この話題が月12件あるのに定型文が無い」と出す → 人が文面を決める → 既存の管理画面で保存
- fail-closed の流儀と同じ

## 7. 工数

| | |
|---|---|
| 回収（sync＋マスク＋辞書分類） | 3h |
| API＋画面 | 2h |
| 保持期間の自動削除 | 0.5h |

**先に1週間だけ回収して件数を見る**のも手（辞書の設計が実データで決まる）。
