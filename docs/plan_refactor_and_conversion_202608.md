## 3. SSoT 一元化【本計画の本丸・A】

### 3-1. 現状の問題

同じ事実が**3系統に重複**しており、片方だけ直すと必ずズレる。§2 の事故はこの構造が原因。

| 事実 | ①SSoT `propertyFacts.ts` | ②`data/properties.ts` | ③`data/{kiyokawa,takasago}Data.ts` | ④`lib/seo.ts` |
|---|---|---|---|---|
| 評価 4.77 / 4.67 | ○ | ○ | ○（×5言語） | ○（説明文に直書き×5言語） |
| レビュー件数 47 / 36 | ○ | ○ | ○（×5言語） | ○（構造化データ） |
| 定員 7 / 6 | ○ | — | ○（×5言語） | ○ |
| チェックイン/アウト時刻 | ○ | — | ○（×5言語・案内とハウスルールで別々） | — |
| アクセス所要時間 | ○ | — | ○（×5言語） | — |

**影響**: レビュー件数を1つ更新するのに最大 **20箇所以上**の修正が要る。
実際に §2 の時刻ズレ（4言語×2物件）はこれで発生した。

### 3-2. 方針

**表示に使う事実は必ず SSoT（Firestore `property_facts` → `propertyFacts.ts`）から取る。**
静的データファイルは「言語ごとの文章テンプレート」だけを持ち、数値を持たない。

```
Firestore property_facts（編集は /admin/properties）
        ↓ getPropertyFacts()
  propertyFacts.ts（型・既定値・フォールバック）
        ↓
  ┌─────────┬──────────┬─────────┐
  物件ページ   比較表・FAQ   構造化データ(seo.ts)
```

### 3-3. 移行手順（壊さない順序）

| 段階 | 内容 | 検証 |
|---|---|---|
| 3-3-1 | `data/properties.ts` の rating/reviewCount を SSoT 参照に置換し、重複定義を削除 | 物件カード・レビュー欄の表示が変わらないこと |
| 3-3-2 | `lib/seo.ts` の構造化データを SSoT 参照に統一（現状 `PROPERTIES` 経由） | Rich Results Test で aggregateRating が同値 |
| 3-3-3 | `seo.ts` の**説明文に直書きされた 4.77** を撤去（文言から数値を外すか、テンプレート差し込みに） | meta description に数値の食い違いがないこと |
| 3-3-4 | `{kiyokawa,takasago}Data.ts` の時刻・定員・アクセスを差し込みテンプレート化（`{checkinTime}` 等） | 5言語×2物件の全ページを目視 |
| 3-3-5 | `faqData.ts` の数値も同様に差し込み化 | FAQ の数値が SSoT と一致 |

**原則**: 各段階ごとにビルド＋デモ確認を挟む。一括置換はしない（§2 で私が
ギャラリーボタンを誤爆したのと同じ事故を避けるため）。

### 3-4. 段階3-3-3の注意

`seo.ts` の説明文は**SEOで実際に検索結果に出る文言**であり、数値を消すとCTRに影響しうる。
差し込み化（`Airbnb評価★{rating}`）が望ましいが、**5言語の文章構造が言語ごとに違う**ため
機械置換できない。1言語ずつ手で確認する必要がある（この段階だけで0.5人日）。

## 4. 予約判断カード【A・0.7人日】

### 4-1. 目的

CTA直前で旅行者が判断するのは価格だけではない。**安全性・取消・サポート・手間**の
不確実性を下げることで、CTAへの到達率ではなく**CTA後の離脱**を減らす。

### 4-2. 設置場所

物件ページのヒーローCTA直下、および下部CTA直下（`PropertyDetail.astro` の
`.pd-hero-ctas` と `.pd-direct-band`）。

### 4-3. 表示要素（すべて SSoT・実装済みの事実から自動生成）

| 要素 | 文言（ja） | 出典 |
|---|---|---|
| 直販価値 | 公式予約なら、空室と総額をその場で確認。 | 固定文 |
| 価格透明性 | 表示総額に清掃料・宿泊税を含みます。現地でのお支払いはありません。 | 固定文（特商法と同義） |
| 取消 | 無料キャンセル：チェックイン日の8日前まで。 | SSoT（`freeCancelDays`）|
| 決済 | 安全なカード決済。カード情報は Stripe が処理し、当社は保存しません。 | 固定文 |
| サポート | ご予約前のご質問には24時間以内に返信します。 | 固定文（サイト全体の約束と一致） |

**重要**: 取消の「8日前」は現状コードに定数として散在している（`checkout.astro` の
`- 8 * 86400000`、`faqData.ts` の文言、`terms.astro`）。**この機会に SSoT 化する**
（`PropertyFacts.freeCancelDays: number`）。しないと §3 と同じ重複を新たに作ることになる。

### 4-4. 実装しないこと

日付を動的計算して「無料取消: 2026年8月22日 23:59 まで」と出す案は、**物件ページでは採らない**。
物件ページの時点では宿泊日が未確定で、日付を出すと誤解を招く。
動的な日付は日程確定後（`/book` 以降）で既に表示済み。

## 5. OTA導線の再設計【B・0.3人日】

### 5-1. 現状

トップページで公式予約・Airbnb・Booking.com が**同じ重さのボタン**で並ぶ。
比較検討のために離脱しやすい。

### 5-2. 変更（発注者指示: ボタンではなくテキスト＋リンク）

- 公式予約を**主CTA（青ボタン）**として視覚的に優先
- OTAは**テキストリンク**に降格。役割を「予約先」から「**レビューの確認先**」へ
- 文言例: 「Airbnb のレビューを見る（47件・★4.77）」「Booking.com の評価を見る」

### 5-3. 表現の制約（重要）

「OTAより安い」と**断定しない**。実際の価格差は Beds24 のレート設定に依存し、
常に保証できないため。代わりに保証できる事実だけを書く。

- 日程を選んだ時点で総額が出る（追加費用なし）
- 予約前に直接相談できる
- 公式サイトのローカルガイド

## 6. Meta コンバージョンイベント再設計【A・1.5人日】

外部プランの妥当性を検証した。**方向性は妥当**だが、現状把握に誤りが1点ある。

### 6-1. 外部プランの検証結果

| プランの記述 | 検証 |
|---|---|
| 「OTAクリックを Lead として送信している」 | **要確認**。現行コードは `data-cta-location` で GA4 送信。Meta Lead 送信の有無を実測する |
| 「直販 Book now で GA4 begin_checkout のみ、Meta InitiateCheckout なし」 | **正しい**。`book/index.astro` に `begin_checkout` のみ確認 |
| 「Purchase のサーバー送信が未確認」 | **正しい**。現状 GA4 purchase は送信、Meta Purchase は未実装 |
| Purchase を最終CVにする | **妥当**。決済成功＋予約番号確定をサーバーで確認してから送る設計に賛成 |
| ViewQuote を最終最適化先にしない | **妥当**。見積表示は売上ではない |

### 6-2. 段階的実装（Purchase を最優先）

| 段階 | 内容 | 理由 |
|---|---|---|
| 6-2-1 | **Purchase をサーバー送信**（CAPI・決済成功＋予約番号確定時） | 売上が計測できないと ROAS が出ない。最優先 |
| 6-2-2 | **InitiateCheckout** を直販 Book now に追加（Pixel＋CAPI・同一 event_id） | 立ち上げ期の最適化先。Purchase が貯まるまでの代替 |
| 6-2-3 | **OTAクリックを OutboundBookingClick に分離**（Lead から外す） | 直販の見込みとOTA流出を混ぜない |
| 6-2-4 | Lead を問い合わせフォーム成功送信に限定 | 同上 |
| 6-2-5 | Search / ViewQuote / ViewContent | 中間指標。ここは後回しでよい |

### 6-3. 送ってはいけない情報（厳守）

氏名・メール・電話・パスポート・住所・**具体的な宿泊日**・決済番号・カード情報を
`custom_data` に入れない。リードタイムは `lead_time_bucket`（例 `8_14_days`）に丸める。

**現行のプライバシーポリシーとの整合**: §4 に Meta ピクセルを追記済み（2026-08-16）。
**自動詳細マッチングはオフのまま**運用する前提のため、CAPI で `user_data`（ハッシュ化
メール等）を送る場合は**ポリシーの再改定が必要**。6-2-1 の実装時に判断する。

### 6-4. 重複排除

Pixel と CAPI で同一イベントを送る場合、同じ `event_id`（予約IDを利用）を両方に含める。
Purchase は予約IDが一意なので、これをそのまま使えば二重計上が構造的に起きない。

## 7. 静的データのリファクタリング【B・1.5人日】

### 7-1. 現状

`kiyokawaData.ts` 1,800行 / `takasagoData.ts` 1,750行。5言語分の全文が1ファイルに直列。

**問題**: 1言語だけ直すつもりが他言語に波及する／言語間の差分が目視できない／
§2 の「日本語だけ正しい」状態を発見できなかった原因でもある。

### 7-2. 方針

```
src/data/properties/
  ├ _schema.ts        型定義
  ├ kiyokawa/ja.ts    言語ごとに分割
  ├ kiyokawa/en.ts
  └ …
```

### 7-3. 言語間整合チェックの自動化（これが本命）

分割より重要なのは、**言語間で数値がズレたら CI で落とす**仕組み。

```ts
// 例: 全言語のテキストから時刻を抽出し、SSoT と一致するか検証
test("表示時刻が全言語で SSoT と一致する", () => { … })
```

§2 のような事故は**人間のレビューでは見つからない**（5言語×2物件×複数箇所）。
機械的に検証する以外に再発を防ぐ方法がない。**7-3 を 7-2 より先に実装すべき**。
