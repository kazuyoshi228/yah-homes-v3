# 仕様書: 問い合わせフォームの内容を Beds24 受信箱にも届ける

**作成**: 2026-08-16 ／ **状態**: 承認待ち（未着工）
**発注者要件**: 「Airstar が Beds24 だけ見ていれば、予約もお問い合わせも全部拾える状態にしたい」
**更新**: 2026-08-16 宛先を清川固定 → 問い合わせ専用物件（346442）に変更（発注者提案）

---

## 1. 背景と課題

現在、問い合わせフォーム（未予約者）からの連絡は次の3経路に届く。

| 経路 | 状態 |
|---|---|
| 通知メール（送信先メールアドレス管理の宛先） | 稼働中 |
| 管理画面 `/admin/messages`（💬お問い合わせ・未読バッジ） | 稼働中 |
| **Beds24 受信箱** | **届かない** |

Beds24 のメッセージは `bookings/messages`＝**予約IDに紐づくもの**しか存在せず、
予約のない問い合わせは入れる先がない。結果、Airstar が Beds24 だけを見ていると
問い合わせを取りこぼす。運営を引き渡すうえでの構造的な穴。

---

## 2. 調査でわかったこと（2026-08-16 実データ）

Beds24 の当アカウントには **`inquiry` ステータスの予約が実在**する（id 91284328・清川）。
これは「直販メッセージの返信テスト用」として作られたもので、備考に
「在庫に影響しない問い合わせステータス」と記録がある。

- 予約ステータスの内訳（清川・全40件）: `new` 38 / `confirmed` 1 / **`inquiry` 1**
- `inquiry` 予約にも `bookings/messages` でメッセージを投稿できる（既存実装 `noteBeds24Message` がそのまま使える）

**未検証（実装の第1ステップで潰す）**: `inquiry` が在庫を塞がないことの実証。
既存 inquiry 予約の日程（2027-06）が販売期間外で `numAvail=0` のため、
その予約の影響を切り分けられなかった。**「塞がない」は備考の記述と Beds24 の
一般的な仕様に基づく推定であり、当アカウントでの実測ではない。**

---

## 3. 方式（2案の比較）

### 採用: B案 — 問い合わせ1件につき `inquiry` 予約を1件作る

問い合わせを受けたら Beds24 に `status: "inquiry"` の予約を作成し、
以降そのスレッドのやり取りを `bookings/messages` で同期する。

- 1問い合わせ = 1スレッド。Beds24 受信箱で会話が混ざらない
- Airstar は予約と同じ操作で返信できる（新しい操作を覚えなくてよい）
- 既存の `inquiry` 実績があり、Beds24 側の想定内の使い方

### 不採用: A案 — 「問い合わせ受信箱」ダミー予約1件に全部流す

- 全問い合わせが1スレッドに混ざり、誰の質問か毎回書く必要がある
- 予約が増えるほど受信箱が読めなくなる
- 採用理由がない（B案が実現可能と判明したため）

## 4. 詳細仕様

### 4-1. 問い合わせ受信時（`contact()` に追記）

`threads` 作成後、非同期で Beds24 に inquiry 予約を作成する。

| Beds24 フィールド | 値 |
|---|---|
| `roomId` | **715198**（物件「yah.homes 問い合わせフォーム用」/ propertyId 346442）|
| `status` | `"inquiry"` |
| `arrival` / `departure` | **翌日 / 翌々日**（1泊・ダミー） |
| `firstName` / `lastName` | 問い合わせ者の氏名 |
| `email` | 問い合わせ者のメール |
| `numAdult` | 1 |
| `price` | 0 |
| `custom1` | `yah.homes inquiry / {threadId}` |
| `reference` | `{threadId}` |
| `notes` | `【お問い合わせ】yah.homes 公式サイトのフォームより／棟の指定なし／このカードは予約ではありません` |

**専用物件を宛先にする理由（2026-08-16 発注者判断）**: 当初は清川に固定する案だったが、
発注者の提案により **問い合わせ専用の物件**（旧 test1・346442）を宛先とする。これにより:

- **在庫リスクが消える** — この物件は本番サイトに出ない（`BOOK_TEST_PROPERTY=1` のデモビルド限定）。
  仮に inquiry ステータスが在庫を塞いだとしても、塞ぐのは誰も予約できない物件であり、
  清川・高砂の販売機会には一切影響しない
- **清川・高砂の受信箱が汚れない** — 予約のやり取りと問い合わせが混ざらない
- Beds24 上の物件名も「yah.homes 問い合わせフォーム用」に改名済みで、Airstar から見て役割が自明

**日程をダミーにする理由**: Beds24 の予約は日程が必須。
過去日付は Beds24 側で拒否されうるため、直近の未来日を使う。

### 4-2. メッセージの同期

既存の予約スレッドと同じ扱いにする（`noteBeds24Message` を流用）。

- **お客様 → 運営**: `source: "guest"` で Beds24 へ。Airstar は受信箱で気づける
- **運営 → お客様**: 管理画面から送った返信も `source: "host"` で Beds24 へ複製（記録の一元化）
- **Beds24 側からの返信**: 今回のスコープ外（Beds24 で返信してもお客様には届かない）
  → 4-4 の但し書きで運用回避する

### 4-3. 失敗時の扱い

**Beds24 への書き込みが失敗しても、問い合わせの受付自体は成功させる。**
（現在の3経路は生きているため、Beds24 同期は「あれば便利」の位置づけ。
ここで例外を投げるとお客様がフォームでエラーを見ることになり、本末転倒）
失敗は `logger.warn` に記録し、`/admin/health` で拾えるようにする。

### 4-4. 運用ルール（マニュアルに追記）

> 💬お問い合わせが Beds24 の受信箱にも表示されるようになりました。
> ただし **返信は必ず管理画面（yah.homes の「メッセージ」）から**行ってください。
> Beds24 側で返信してもお客様には届きません（このカードは実際の予約ではないためです）。

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| ~~在庫を塞ぐ~~ | **解消**。宛先を本番非公開の専用物件（346442）にしたため、清川・高砂の在庫に影響しない |
| **スパムで Beds24 が予約だらけになる** | 同一メール・同一IPから短時間の連投は Beds24 へ送らない（Firestore 側の受付は従来どおり）。上限は1メールアドレスあたり1日3件 |
| **売上レポートに混ざる** | `price: 0`・`status: inquiry` のため売上には計上されない見込み。5-3 で Beds24 のレポート画面を目視確認 |
| **OTA（Airbnb等）へ同期される** | 専用物件は OTA に接続していないため影響なし（5-3 で目視確認） |
| **Airstar のアカウントから専用物件が見えない可能性** | **要確認（承認事項2）**。清川・高砂は運営会社アカウントからリンクされた物件だが、専用物件（346442）は当社側で作成したもの。Airstar の Beds24 画面にこの物件が出るかを、実装前に Airstar に確認する。見えない場合は共有設定を追加する |
| **E2E決済テストと受信箱が同居する** | 専用物件は決済の通しテストにも使っている。テスト予約と問い合わせが同じ物件に並ぶが、`status` と `notes` で区別できるため実害はない |
| **Airstar が Beds24 で返信してしまう** | 4-4 の運用ルール＋ notes に「このカードは予約ではありません」と明記 |
| **解決済みの問い合わせが受信箱に残り続ける** | 対応完了後、Beds24 側で当該 inquiry を削除する運用（マニュアルに記載）。自動削除は今回スコープ外 |
