# 提案書 — yah.OS のデータ構造改善（強固・シンプル・SSoT・横断検証）

- 状態: **提案・未実装（承認待ち）**
- 起票: 2026-08-25（共有部スレッド）
- きっかけ: 「全体の構造がOSとして強固かつシンプルにSSoT化されており、分析時には横断的に数字を検証できるようにしたい」（発注者）

---

## 0. 先に結論

**横断検証に必要なのは「置き場の統一」ではなく「形の統一」と「検証の常設」。**
データを1か所に集め直す大工事は要らない。読み取り時に単一の形へ射影するレイヤ（B）と、
全検証を1本にまとめた health（A）を足せば、どのカードの数字も同じ道具で検証できるようになる。

---

## 1. 現状の棚卸し — 形が3種類ある

| 形 | 置き場 | 例 |
|---|---|---|
| **フラットコレクション**（1行=1ドキュメント） | equipment・schedules・jobs・contracts・cvr・taxes・insurance・reserves・scorecards | 設備74行・契約17行・CVR10行 |
| **物件ドキュメント内の埋め込み配列** | properties/{id} の supplies（153行）・construction（20行）・investment・additionalInvestment・requiredDocs・drawings | 備品・工事の明細 |
| **コード内の定数** | CAP_RATE=0.05（props.ts）・DEFAULT_FACTOR=2.0 / DEFAULT_CAP=30（lifecycle.ts） | 還元利回り・使用強度 |

強いところ（維持する）:
- 派生値を保存しない（実効年数・年割り・追加投資は毎回計算）
- 突合・監査・txNo血統・消し込みの書き戻し（物件カードは既に自己検証する）
- fail-closed（業者未定はAIが動かない）

弱いところ（この提案の対象）:
- **横断の検証がない**。カード内の監査はあるが、「融資カードの月返済 ↔ 月次の返済行」「売上レポート ↔ 利回りの分子」のような**カードをまたぐ不変条件は誰も見ていない**
- 金額の形がバラバラ（amount / amountPerYear / premiumPerYear / price…）で、横断集計のたびに専用コードを書いている
- 埋め込み配列は行IDが無く、1行だけの更新・参照ができない（毎回配列を丸ごと書き換えている）
- 事業の係数がコード・物件ドキュメント・assumptions の3か所に散在

## 2. 提案（優先順）

### A. `health` — 全検証を1本の endpoint に常設する（強固・横断検証の本丸）

いま検証は「物件カードを開いたときに物件の監査が走る」形。これを**システム全体の不変条件を
毎回すべて実行して返す1本**にする:

```
GET ?action=health →
{ checks: [ {card, name, ok, detail}, … ], summary: {ok: 41, warn: 2} }
```

中身は既存の検証の寄せ集め＋**カード横断の新規5本**:

| 種別 | 検証 | 今 |
|---|---|---|
| カード内 | 投資額・追加投資の突合／txNo血統／二重計上／group未宣言／耐用年数の欠測 | ✓ あり（propsに散在） |
| カード内 | 期日超過ジョブ／見積催促／契約の期限・原本未登録 | ✓ あり（alerts・contractsに散在） |
| **横断** | 融資カードの月返済合計 ↔ 財務（月次）の返済行 | ✕ 新規 |
| **横断** | 売上レポート12ヶ月 ↔ 利回りカードの分子 | ✕ 新規 |
| **横断** | 修繕積立（固定費） ↔ 年割り合計（更新計画）＝判定の警報化 | △ 表示のみ |
| **横断** | CVRの検算（閲覧÷表示＝検索→閲覧、±0.06pt） | △ 取込時のみ |
| **横断** | 保険料（固定費の合計） ↔ insurance 各行の合計 | ✕ 新規 |

効能: ①分析の前に必ず `health` を1回叩けば**全数字の信頼度が分かる**（AIの分析手順が
「health → 本題」の2手に固定される）②以前のレビューのP1（今日ボード）・P2（ドット実データ化）は
この endpoint の**表示先にすぎなくなる**——1本で3つ片づく。

### B. `facts` — 全金額行を単一スキーマへ射影する読み取りレイヤ（横断分析の本丸）

**保存はしない**（SSoTを崩さない）。読み取り時に、散らばる金額行をぜんぶ同じ形に潰して返す:

```
GET ?action=facts[&prop=&ym=&flow=] →
[ { prop, ym, amount, flow, group, label, txNo?, source, docPath }, … ]

flow = invest（初期投資）| add（追加投資）| fixed（税・保険・積立）| opex（光熱費等）
     | revenue（売上）| loan（返済）| future（長期修繕の概算）
docPath = その数字の正本の場所（equipment/kiyokawa-lt-gaiheki など）
```

- 「2025年3月に全カテゴリでいくら使ったか」「清川と高砂の固定費差」のような横断の問いが
  **全部この1本のフィルタ・集計になる**。カードごとの専用コードが要らなくなる
- `docPath` で**どの数字も正本まで一発で遡れる**（血統の完成形）
- AIの分析はこう変わる: 「health を叩く → facts を叩く → 集計する」。カードのAPIを
  1つずつ読んで形を解釈する作業が消える

### C. 埋め込み配列をフラットコレクションへ統一（シンプル・強固）

properties ドキュメント内の supplies（153行）・construction・investment・additionalInvestment を、
equipment と同じ「1行=1ドキュメント」へ移す（`items` コレクション・`kind` で区分）。

- 行IDが付く → 1行だけの更新・参照・リンクができる（今は毎回配列を丸ごと書き換えている）
- 物件ドキュメントの肥大（1MB上限）リスクが消える
- **形が1種類になる**: 「金額の明細はぜんぶフラットコレクション」——B の射影も単純になる
- **タイミングが重要**: 高砂のデータ投入前にやる。後からだと移行対象が2倍になる

### D. 係数を assumptions コレクションへ集約（SSoT）

CAP_RATE（コード）・usageFactor / lifespanCapYears / buildingLifeYears（物件ドキュメント）・
management-fee（assumptions）を、**assumptions に一本化**（物件別の係数は prop 付きの行）。
コードの定数はフォールバックに格下げ。

- 「cap を 5%→5.5% に変える」が**デプロイではなくデータ変更**になる
- `?action=assumptions` で**事業の前提ノブが全部1画面に並ぶ**——分析AIが前提を確かめる場所が1つになる

### E. スキーマ台帳 — `docs/schema.md`（横断分析・並行スレッドの共通言語）

コレクション・フィールド・単位・誰が書くか・派生規則を1枚に。新しいカードスレッドと
分析スレッドが**リバースエンジニアリングなしで**データを扱えるようになる。
CLAUDE.md から参照。書いたら陳腐化させない——スキーマを変えるPRはこの表も直す（共有部スレッドの責務）。

### F. agency DB の日次バックアップ — Firestore標準機能で（強固・保険）

**Firestore標準のスケジュールバックアップを使う（2026-08-25 発注者指摘で簡素化）。**
当初案の export＋Cloud Scheduler は過剰だった。標準機能なら1コマンド・コード不要:

```
gcloud firestore backups schedules create --database=agency --recurrence=daily --retention=7d
```

同じものを default（Web SSoT）・chat にも。復元は新DBへの丸ごと復元。費用は保管ぶんのみ。

### G. 保存済み導出値の掃除（焼き付け・保存の最小化 — 2026-08-25 発注者方針で新設）

棚卸しで見つかった「導出できるのに保存されている値」を消す:

| 保存されているもの | 処置 |
|---|---|
| `investmentTotal`（¥68,092,172）・`suppliesTotal`・`constructionTotal` | **削除**。表示は既に導出値を使っており、保存値は更新漏れの温床でしかない |
| 投資額のリフォーム8行・追加投資6行（突合用に残した保存行） | **削除**。表示を完全導出化した時点で「保存側が腐る」余地ごと消せる。突合の監査項目も整理（txNo血統・二重計上・group未宣言は残す） |
| 手動ドット（localStorage） | **A実装後に削除**して health 連動へ（旧P2） |
| キャッシュ（sessionStorage） | 残す（一時値であり正本ではない） |
| cvr・equipment・契約などの一次事実 | 残す（これが正本。削減対象ではない） |

原則の明文化: **保存してよいのは一次事実（いつ・いくら・出典）と人の判断（承認・係数・宣言）だけ。
合計・割り算・並び替えで作れるものは保存しない。** CLAUDE.md に転記する。

---

## 3. やらないこと（シンプルさの防衛）

- **BigQuery / BIツール / DWH**: 2棟・数百行の規模で導入する道具ではない。facts 射影で
  横断分析の9割は満たせる。5棟＋直販が回り出してデータ量が桁を超えたら再検討
- **新しいカード**: 器は足りている。health は index（今日ボード）と既存カードに出す
- **書き込み側の共通スキーマ強制**: 移行済みの equipment 等はそのまま。強制は C の移行時に自然に達成される
