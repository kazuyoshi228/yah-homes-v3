# 指示書: 定期レポートに RevPAR の推移を出す（2026-09-02 発注者指示）

**担当: 定期レポート（reports.html / reports.js）のカードスレッド**
共有部スレッドが数字の検証まで行い、実装はカード担当へ申し送る。

## なぜ要るか

いまの月次報告は **ADR と稼働率が別々**に出ている。この2つは掛け算しないと意味が読めない。

実測（清川14ヶ月・高砂11ヶ月）で分かったこと:

- **ADRと稼働の相関係数は ＋0.38**。値上げと稼働はトレードオフになっていない
- 清川は ADR ¥35,410 → ¥46,353（+31%）と上げながら、稼働も 62% → 69% に上げた
- **ところが RevPAR は1年間ほぼ横ばい**
  - 2025年後半 ¥34,306 ／ 2026年前半 ¥34,216 ／ 2026年後半 ¥33,441

**ADR単体を追うと、稼働を犠牲にして数字だけ良く見せられてしまう。**
値上げが効いたのか稼働を失っただけなのかは、掛け算でしか判定できない。

## 出すもの

**RevPAR ＝ ADR × 稼働率**（1室1泊あたりの実力）。単位は円／泊。

- **保存しない。** `revenue` の `adr` と `occ` から毎回計算する（SSoT）
- 棟ごとの月次推移と、全棟の合成
- 前年同月との比較（季節性があるため、前月比では判定できない）
- 半期の平均（上の表の形）

## 注意

- **月をまたぐ平均は、単純平均ではなく泊数で重みづけること**。稼働の低い月が実力を押し上げて見える
- 稼働率は `occ`（整数％）で入っている。100で割ってから掛ける
- 高砂には宿泊以外の収入（オフィス賃料 月¥100,000）があるが、**RevPARには入れない**——1室1泊の実力を見る指標なので
- 六本松（2027-02）・大手門（2027-04）が稼働したら、自動で並ぶようにしておく

## 目標として置く数字

**2026年後半の ¥33,441 を、いつ・どこで上回るか。** これが横ばいを抜けたかどうかの判定線になる。

## 出どころ

Firestore `agency` DB / `revenue`（kind: monthly）。運営会社の売上収支報告書PDFが正本。
