## なぜやるか

**事業が1つだから、コードも1つにする。** これが根拠のすべてで、以下はその帰結である。

yah.homes は「お客様が予約する場所」、chat.yah.homes は「泊まったお客様が質問する場所」、
os.yah.homes は「それを運営する場所」——**同じ宿に泊まる同じお客様の、同じ体験の3つの面**である。
分ける理由が事業側にない。

2026-09-03 の議論がその証拠になった。直販を開ける話は yah.homes と os.yah.homes の
両方に関わり、RevPAR は運営の数字で、予約明細は決済システムの中にある。
**別の話として扱おうとしたものが、全部つながっていた。**

以下は、その帰結として実際に効いていること。

**① 全体が見えない**
yah.OS の全体像を知るには2リポを頭の中で合成する必要がある。
カード33枚は yah-os、それを支える45ファイルは v2。片方だけ見ている人は半分しか見えない。
「このカードの数字はどこから来るのか」を辿るのに、毎回リポをまたいでいる。

**② 探索の遅さが、間違いになる**
この日の作業で実際に起きた失敗:
- 存在しない `finance.js` を grep して空振り（スクリプトは HTML に内包されていた）
- `properties.investmentTotal` を確認せず使い、VIEW が落ちた
- `bq-verify.mjs` を置く場所を間違え、`firebase-admin` が解決できなかった

どれも「全体が見えていれば起きなかった」種類のもの。
**構造が単純なほど間違えにくい**——今日 derive.ts でやったのと同じ理屈である。

**③ カードとエンドポイントが対になっている**
この日、カードを直すたびに `agencyApi` も直した。**5回**（cashflow・personal・properties・
finance・realestate）。1リポなら1コミットで済み、CIも1回で通る。

**④ CLAUDE.md が実態と噛み合っていない**
「リポをまたぐ変更をしない」と書いてあるのに、毎日またいでいる。
ルールが形骸化している状態は、他のルールの重みも下げる。

**⑤ 新しく作るものの置き場が迷わない**
まさにこの日、MCPサーバーをどこに置くかで往復した。1つなら発生しない議論だった。

**⑥ 承継**
50年以上持つ計画で、承継は採点の最低項目（30点）。
「宿泊事業のコードはこの1つ」と言えるほうが、3つを説明するより明らかに引き継ぎやすい。

### 逆に、統合しても解決しないこと

- **守秘は改善しない。** リポの境界では守っていない。守っているのは
  `firestore.agency.rules`（全面拒否・Functions経由のみ）と `agencyApi` の認証。
  統合しても1ミリも変わらない
- **今日の3つの事故は防げない。** NOIが4か所で違った・SQLがずれた・確認せず書いた
  ——すべて derive.ts / derivecheck.mjs / bq-verify.mjs で別に解決済み
- **Firebaseプロジェクトの共有は残る。** eSIM事業と `yah-homes` を共有している事実は変わらない

## 山場: `deploy.sh` の門番

**いちばん効いている安全装置を、弱くしてはいけない。**

いまの yah-os の `deploy.sh` は「ツリーが clean かつ origin/main と一致していないと止まる」。
CLAUDE.md にこうある:

> これは**別スレッドの書きかけファイルが本番に混入するのを防ぐ門番**。壊さない・迂回しない

**1リポにすると、chat の書きかけが yah.OS のデプロイを止める。**
並行作業が日常なので（この日も v2 に別スレッドの未コミットが2件あった）、毎日起きる。

### 対策案

**案1: 変更範囲で判定する（推奨）**
```sh
# apps/os を出すときは、apps/os 配下だけが clean であればよい
git status --porcelain -- apps/os functions/src/agency | grep . && exit 1
```
- 利点: 仕組みが単純。いまの門番の思想を保てる
- 注意: `functions/src/agency` も見る必要がある（カードとエンドポイントは対）

**案2: git worktree を分ける**
- 利点: 物理的に混ざらない
- 欠点: 運用が重い。統合の目的（すっきりさせる）に反する

**案1で行く。** ただし**「どのディレクトリがどのデプロイに属するか」の対応表**を
`deploy.sh` の中に明示し、増えたときに直し忘れないようにする。

## CI を分ける

いま合計7本。統合すると、1文字直すたびに全部回る。

GitHub Actions の `paths:` フィルタで分ける。

```yaml
on:
  push:
    paths: ['apps/os/**', 'functions/src/agency/**']
```

| ワークフロー | 監視するパス |
|---|---|
| os のゲート4本 | `apps/os/**`, `functions/src/agency/**` |
| web のデプロイ | `apps/web/**` |
| functions のデプロイ | `functions/**` |
| chat のCI | `apps/chat/**`, `functions/src/chat/**` |

**検査スクリプトの相対パスを直す必要がある**（`typecheck.mjs` などは
カレントディレクトリ基準で書かれている）。
