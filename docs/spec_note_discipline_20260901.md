# 注記の規律（サブコピー・注記を増やさない仕組み）

**2026-09-01 ／ 発注者からの問い「なるべくサブコピーや注記が少なくなるようにガイドラインに制定したら、効果ありますか？」に対する仕様書**
正本の置き場: デザインガイドライン（`design_guideline_yah_os_20260831.md`）§7 に本文を、
機械検査は `yah-os/designcheck.mjs` に置く。

## 0. 結論

**効果はある。ただし「なるべく少なく」と書くだけでは効かない。**
この repo では同じことが金額の焼き込みで起きている——「HTMLに金額を書かない」という文章は
何度も破られ、`check-hardcoded.mjs` のラチェット（現状値を記録し、増えたら CI が落ちる）を
入れた時点で止まった。**数えられる形にして初めて守られる。**

一方で、**削減それ自体を目標にしてはいけない。** いま資金繰り・BSに残っている注記の多くは
「なぜ二重計上していないか」の説明であり、消すと数字の誤読を招く。
本仕様は「減らす」ではなく **「置き場所を決める」** ための規則である。

本当に読ませたい警告（要対応・前提の断り）が埋もれる。これが実害。

## 2. 規則

### 2.1 注記は3種類だけ

| 種類 | 何を書くか | 例 |
|---|---|---|
| **出典** | どの台帳の、いつ時点の数字か | 「通帳の記帳日: 2026-08-03」 |
| **前提** | 導出に使った係数・期間・除外 | 「稼働見込みは実績と別列。合算していない」 |
| **警告** | 人の対応が要ること | 「原本が未登録」 |

**この3つ以外は書かない。** とくに **「使い方の説明」を書かない**——
それは画面の設計が足りていないサインであり、文章ではなく UI で解決する（§2.3）。

### 2.2 量の上限

- **1画面あたり注記ブロックは 3つまで**（表の行内に付く短いラベルは数えない）
- **1つ 60字まで**。超えるものは `<details>` で畳むか、docs 側へ逃がしてリンクする
- 60字を超える説明を画面に置きたくなったら、**それは仕様書に書くべき内容**

### 2.3 注記に書くくらいなら、こちらに埋める（優先順）

1. **列名・タブ名** — 「稼働見込」という列名があれば「これは見込みです」という注記は要らない
2. **空状態の文言**（`.panel-empty`・空セル） — 「◯◯を選択すると表示されます」はここに書く
3. **要素の近くの1語**（バッジ・ピル） — 「未」「要対応」
4. それでも足りないときだけ注記

**効果はこの置き換えの方が大きい。** 削除ではなく移動である。

## 3. 機械検査（`designcheck.mjs` に追加）

### 3.1 数え方

- 対象: `.html` と `.js`（JSへ移して検査をすり抜けられないように——金額検査と同じ理由）
- `<style>` ブロックは除外
- `class` に `note` / `dim` / `hint` / `caption` を含む要素の直後テキストで、**8文字以上**のもの
- 数えるのは **件数** と **最長文字数**

### 3.2 ラチェット

`designcheck.mjs` に基準表を持つ（金額検査と同じ形式）。

```
const NOTE_BASELINE = { "properties.js": 85, "reports.js": 76, ... };
```

- **基準を超えたら CI が落ちる。**（＝これ以上増やせない）
- **下回ったら、その場で基準を下げてコミットする**（ラチェット＝戻らない）
- **新規ファイルの基準は 3**（§2.2 の上限）。新しいカードは最初から規則どおりに作る
- **単一の注記が 60字を超えたら落ちる。** ただし既存の超過分は初回のみ免除リストに入れ、
  触ったときに直す（一斉書き換えはしない——カードスレッドの作業と衝突するため）

### 3.3 やらないこと

- 文章の質（分かりやすさ）は機械で測らない。**量と置き場所だけを守る**
- 既存 543件の一斉削除はしない。**触ったカードから減る**形にする

## 4. 進め方

| 段 | 内容 | 担当 |
|---|---|---|
| 1 | ガイドライン §7 に §2 を追記（v1.8.0） | 共有部スレッド |
| 2 | `designcheck.mjs` に §3 の検査を追加。現状値で基準表を作る（**この時点では誰も落ちない**） | 共有部スレッド |
| 3 | 60字超の免除リストを作る（現状 30件強の見込み） | 共有部スレッド |
| 4 | 以後、各カードスレッドが自分のカードを触るときに §2.3 の置き換えを行い、基準を下げる | 各カードスレッド |

**段2までが本仕様の実装範囲。** 段4は強制せず、ラチェットが自然に効く。

## 5. 想定される反発と回答

- **「注記が書けないと不親切では」** — 書けなくするのではなく、3種類・60字に絞る。
  それ以上の説明が要る画面は、画面の側を直す
- **「既存が多すぎて守れない」** — ラチェットは現状値から始めるので、いまの画面は落ちない。
  増やすことだけを止める
- **「JSで生成した注記はどう数えるのか」** — テンプレート文字列の中も同じ正規表現で数える。
  動的に差し込む値（`${}`）は文字数に含めない
