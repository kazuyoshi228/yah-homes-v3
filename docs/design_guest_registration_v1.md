# 宿泊者名簿の自社フロント化 v1（設計書・承認待ち）

- 起票: 2026-08-18（発注者との対話から）
- 状態: **ドラフト＝未承認・未着工**。着手前に「6. 未決事項」の回答が必要
- 背景: 現在の名簿は Airstar の Zoho Forms（清川=zfrmz.jp / 高砂=forms.zohopublic.jp）。
  入力画面・保存先ともZoho側にあり、5言語非対応・予約情報のプリフィル不可・
  旅券画像の取得なし・自社に顧客データが残らない。

## 1. 目的（優先順）

1. **法令適合の強化** — 名簿の法定項目＋（国内住所なし外国人の）旅券の写しを、3年保存の
   管理下に置く。※現行フォームは旅券画像を取得しておらず、厚労省通知・自治体要綱の
   要求を満たしていない恐れがある（→6-1 保健所確認）
2. **入力体験** — 5言語・yah.homesデザイン・予約情報（氏名/日程/人数/棟）プリフィル。
   チャットFAQで頻出の「宿泊場所の欄が分からない」等の混乱を構造的に消す
3. **全チャネルの顧客ID化** — Airbnb/Booking経由のゲストのメールアドレス等が
   名簿提出時に自社DBへ入り、`guest_profiles` に紐づく（リピーター直販の入口）

## 2. URL設計

| 用途 | URL | 備考 |
|---|---|---|
| 正 | `https://yah.homes/register/{token}` | 予約別トークン。言語プレフィックス無し（トークンから予約言語を引いて初期表示・ページ内で切替） |
| 短縮 | `https://yah.homes/r/{token}` | OTAメッセージ・SMS向け。301で正へ |
| フォールバック | `https://yah.homes/register/` | トークン無しで開いた場合、予約番号＋姓で照合してトークンを発行 |

- 「register」を採用する理由: 名簿=guest registration として英語圏ゲストに意味が通る。
  `checkin` は暗証番号の提示を期待させるため不採用（番号はこのページでは出さない）。
- 全URL noindex。SSoT の `registerUrl` を新URLへ切り替えるだけで、確定メール・
  チャット・基本情報・llms が自動で追従する（切替は施設ごと・Zoho併走期間あり）。

## 3. 画面仕様（/register/{token}）

- 予約読込: トークン → bookings を照合（無効・期限切れは丁寧なエラー＋問い合わせ導線）
- プリフィル: 代表者氏名・日程・人数・棟（棟名と住所はSSoTから表示）
- 入力項目（旅館業法の法定項目）:
  - 全員: 氏名・住所・職業
  - 国内に住所を持たない外国人: 国籍・旅券番号・**旅券画像（カメラ撮影/アップロード）**
  - 同行者は予約人数ぶんの行を自動生成（管理画面のBR方式と同じ思想）
- 同意: プライバシーポリシー（改定版）への同意・`marketingOptIn`（任意・既存踏襲）
- 送信: fail-closed — 保存が完了するまで完了画面を出さない。失敗時は再送を案内
- 完了画面: 「My Pageに保存（メールにワンタイムリンク）」の任意アカウント化ボタン（第2弾）

## 4. データ・API

```
Functions registerToken(発行) / registerSubmit(受領)
  ├ Firestore guest_registrations/{bookingId}
  │    法定項目＋提出日時・言語・トークン消込。3年で自動削除（TTL）
  ├ Storage passports/{bookingId}/{guestN}.jpg
  │    非公開バケット・署名URLのみ・root/admin限定・3年で自動削除
  ├ bookings.registeredAt を更新（前日案内の暗証番号ゲートは既存運用を踏襲）
  ├ guest_profiles へメール/電話で突合（第2弾のAuth基盤）
  └ Airstar連携: Webhook → Zoho Flow（案A・推奨）
       弊社はZohoの認証情報を預からない。Airstar側はノーコードのフロー設定のみ
```

- セキュリティ: 旅券画像は Meta Pixel 等の計測対象外ページで扱う。管理画面からの
  閲覧は root/admin のみ・audit_logs 記録。トークンは推測不能な乱数＋有効期限
- SSoT原則: 施設の表示情報（名称・住所・時刻）はすべて property_facts 参照。直書きしない

## 5. 実装フェーズ

| フェーズ | 内容 | 規模 |
|---|---|---|
| P1（名簿コア） | ページ＋registerSubmit＋Storage/TTL＋トークン発行＋Zoho Webhook＋registerUrl切替 | 2日弱 |
| P2（Auth） | 完了画面からのメールOTPアカウント化・guest_profiles統合 | 1日 |

- Authを必須にしない理由: 名簿提出を認証必須にすると提出率が下がり、
  「名簿未提出→暗証番号を渡せない」既存ゲートと衝突して当日入室不能が増えるため。
