# yah.OS 自動化 仕様書 v1（2026-08-18・承認待ち）

一枚ページ（spec_yah_os_onepager_v1.md）の7カテゴリ19カードを対象に、
「人が回す」を「自動で回り、人は例外と判断だけを見る」に変える設計図。
発注者指示により**レポート類・分析を最優先**とする。

## 1. 設計原則（全自動化に共通）

1. **SSoTファースト**: レポートは数字の写しを作らない。正本（Firestore bookings・
   定点シート・Cockpit・GSC/GA4）から毎回読んで組み立てる。レポート自体は成果物であり正本ではない。
2. **fail-closed**: 取得に失敗したら、古い値や既定値で埋めずに「欠測」と明記して届ける。
   静かに壊れない（サイレント成功が一番危険）。失敗は即時にアラートメール。
3. **実行基盤は Cloud Scheduler + Functions に統一**: Mac のローカル実行に依存しない。
   Beds24 クラウド定点（毎朝8:00・実行SA=appspot）で実証済みの型をそのまま使う。
   ローカルスクリプト（gsc-weekly / organic-weekly / update-teiten-sheet）は段階的にクラウドへ移設して廃止。
4. **人間の承認ゲートは自動化しない**: 公開（published昇格）・返金実行・価格変更・
   広告予算の増減（ツマミ）・PE向け数字の開示は、必ず人間の操作として残す。
5. **通知は既存の型**: 宛先は管理者台帳（notifyTeiten 等のフラグ）。成功は定期サマリ1通に集約、
   失敗だけ即時に届く。通知が増えすぎると読まれなくなり、実質手動に戻る。

## 3. 自動化フェーズ（レポート・分析を先頭に）

### Phase 1 — 週次レポートの全自動化（最優先）

**目標**: 毎週月曜 朝に「先週の yah.homes」が1通のメールで届く。人は読むだけ。

- **1-1. 定点データの自動収集をクラウド化**
  - `gsc-weekly.mjs`（GSC→シート）と `organic-weekly.mjs` を Functions 化し、
    Cloud Scheduler（毎週月曜 06:00 JST）で実行。ローカル版は廃止。
  - 定点シートの予約実績列（清川/高砂の組数・泊数・先付け残高）を、
    Firestore bookings＋Beds24 から自動算出して書き込む（`update-teiten-sheet.mjs` の自動化）。
    J列など発注者の計算列には触らない（現行ルール維持）。
  - ※これは **2026-07決定「週次定点は当面手動」の見直し**にあたる。承認をもって差し替え。
- **1-2. 広告成果の自動取得**
  - Google Ads API・Meta Marketing API から週次で消化額・CV・CPA を取得しシートの広告タブへ。
    市場別（TW/HK/KR…）に分解。種火方式の「ツマミを回す判断」に必要な数字だけに絞る。
- **1-3. 週次サマリメールの合成**
  - 上記＋Beds24週次を1通に合成（予約・稼働・GSC・広告・チャット件数）。
    各項目に前週比。取得失敗した項目は「欠測」表記で送る（原則2）。
  - 宛先は管理者台帳 notifyTeiten。

### Phase 2 — 月次・財務の半自動化

- **2-1. 月次スナップショット**: 毎月1日、前月の確定数字（売上・組数・泊数・チャネル比率・
  広告費）を bookings と広告APIから集計し、Cockpit の月次タブへ書き込み。
  42ヶ月モデルへの反映（前提の更新）は人間の判断のまま。
- **2-1b. 経費の自動取得（2026-08-18 発注者確認: 経理はマネーフォワードで仕訳済み）**:
  マネーフォワード クラウド会計の API（OAuth2）から前月の仕訳データを科目別に取得し、
  月次スナップショットの経費側に合算 → 売上（Stripe＋Beds24）と合わせて**月次P/Lが自動で締まる**。
  - 分類は MF 側で完結しているため、取り込み側での科目判定は行わない（写しの判断を作らない）
  - 発注者作業: MF 開発者ポータルでのアプリ登録とAPI連携の承認（クライアントID発行）。
    APIが契約プランで使えない場合の代替は仕訳帳CSVの手動エクスポート→取り込み口（劣化運転として用意）
  - カードポータル・銀行への直接ログインはしない。明細→MF の同期は現行どおり MF に任せる
- **2-2. yah.OS 財務カードへの供給**: PE向けに開示する数字は、シートの「開示用タブ」から
  デプロイ時に焼き込み（onepager仕様 §6-2）。**開示の実行は必ず人間**（原則4）。
- **2-3. チャット運用レポート**: 会話数・解決率・エスカレーション率・言語分布を月次で集計
  （chat DB から。チャット品質の恐竜化チェックを月1で機械が出す）。

### Phase 3 — 分析・監視の常時化

- **3-1. AirDNA競合調査（2026-08-18 発注者決定）**: **AirDNA Research（月$34・年払い）を契約し、
  月次の定型チェックリスト運用**とする。見る指標・商圏（福岡市中央区）・競合リストを固定した
  チェックリストを用意し、人が月1回15分で埋める。APIは不採用（エンタープライズ契約 年$50K〜で
  規模に不釣り合い）。将来 Phase 5（価格エンジン）着手時に、Beds24 連携のある PriceLabs
  マーケットダッシュボードを市場データ源として検証する（AirDNA API 再検討はその結果待ち）。
- **3-2. PRクリッピング**: Google Alerts 相当（検索API週次）で「yah.homes」言及を週次サマリに同載。
- **3-3. 異常検知**: 毎朝の定点に「しきい値割れ」を追加（例: 直販CVゼロが7日continuous・
  チャットエラー率・メール送信失敗数）。しきい値超過のみ即時アラート。

## 4. 実行基盤の標準形

```
Cloud Scheduler（JST cron）
  └→ Functions（region asia-northeast1・SA=appspot）
       ├→ 読む: Firestore（既定/chat）・GSC API・GA4 API・Ads/Meta API・Beds24 API
       ├→ 書く: 定点シート/Cockpit（Sheets API・発注者の計算列は不可侵）
       └→ 届ける: SMTP（既存 mailHtml テンプレ・宛先は管理者台帳）
失敗時: 即時アラート1通（何が・どこまで成功したか・欠測箇所）＋ mail_logs 記録
```

- 新しい常駐サーバー・外部SaaS（Zapier等）は導入しない。既存の Functions パターンで完結。
- スケジュールは JST で統一し、既存の 6:00 RAG / 7:00・10:00 メール / 8:00 定点 / 9:00 キャンセル監視と衝突しない枠に置く。

## 5. 人間に残す判断（自動化しないことの明文化）

| 判断 | 理由 |
|---|---|
| 記事・ページの公開 | 鉄則1（AIに公開権限を持たせない） |
| 返金の実行 | 金銭・Admin以上の承認ゲート |
| 価格・料金の変更 | 価格哲学（実績トリガーの機械調整は将来の別仕様） |
| 広告予算の増減 | 種火方式の「ツマミ」は人間の意思決定 |
| PE向け数字の開示 | 守秘・タイミングは経営判断 |
| 42ヶ月モデルの前提変更 | 保守基準の規律そのもの |
